## 5. Literature and Technology Review

This chapter reviews the five technology lines named by the official topic sheet for *Victor2 – Enterprise Network Infrastructure and Architect*. For each line it establishes the current state of the art, identifies the candidate technologies, states why the named technologies were selected, records the alternatives considered and rejected, examines the security and operational consequences, and maps the choice onto the assessment domains of the WorldSkills Occupational Standards (WSOS) 2026 for *IT Network Systems Administration* (Skill 2447, WorldSkills Shanghai 2026). Every statement about the standard is taken from the verified extraction held in this repository (`proposal\research\wsos-2026-2447.md`), whose own census (Section 3.7) and audit row (Appendix A) record 131 requirement lines machine-extracted from the published page and re-verified verbatim with 0 mismatches. That pack also carries a corrections section (Section 7, items C1-C6) that supersedes the earlier review it examined — notably C1: Domain 5 lost Python, YANG, RESTCONF and NETCONF for the 2026 edition.

Two preliminary honesty statements are necessary. First, the standard is not a technology checklist. It is organised into six weighted sections — Work organization and management (5 %), Communication and interpersonal Skills (5 %), Data Transfer Networks (25 %), Network and System Operations (25 %), Infrastructure Automation (15 %) and Troubleshooting (25 %) — so 75 % of the assessment weight sits in the three technical 25 % domains. Several technologies the topic sheet names are simply absent from it: `FSRM`, `iSCSI`, `RRAS`, `IKEv2`, `Keepalived`, `nftables`, `WireGuard`, `RSTP`, `ASA`, `Agentic`, `OpenClaw`, `MCP`, `artificial intelligence` and `machine learning` each occur zero times in the 2026 text *and* zero times in the raw HTML of the page. Where this chapter says a technology is "named", the string is present and a verbatim requirement line is quoted; where it is not, the chapter says so and justifies the choice from the topic sheet or from a generic requirement line, labelling the inference a **bridge**. Second, the WSOS 2026 contains no requirement for screen captures: `screen`, `capture`, `screenshot` and `evidence` occur zero times. The obligation to produce findings, manuals, steps, screen captures, verifications and references is a Higher Diploma in Telecommunications and Networking (HDTN) topic-sheet requirement. The standard does require documentation three times, and one line — `Prepare a technical document reflecting the solution in detail for agreement and sign-off` (Domain 6, 25 %) — is the strongest single justification in the standard for this project's documentation weight.

### 5.1 Microsoft Server Networking and Network Services

#### 5.1.1 State of the art

Enterprise directory service has converged on two durable models: the tightly integrated, multi-master directory with bundled identity-adjacent services and a built-in policy engine, and the composable set of single-purpose daemons on Linux assembled by the operator. Two further trends dominate. Remote access has moved from pre-shared keys to certificate-authenticated IKEv2 and TLS-based tunnels; block storage has moved from direct-attached disks to network-attached block devices so that a machine's storage can outlive its host; and file services have acquired policy layers — quotas, file screening, classification — because share permissions alone cannot enforce capacity or content policy.

#### 5.1.2 Candidate technologies

| Capability required | Candidates considered | Named by the topic sheet |
|---|---|---|
| Directory and authentication | Active Directory Domain Services (AD DS); Samba AD DC; OpenLDAP with Kerberos | AD DS |
| Certificate authority | Active Directory Certificate Services (AD CS); OpenSSL driven directly; Easy-RSA | AD CS |
| File services with policy | Windows file server with File Server Resource Manager (FSRM); plain NTFS permissions; Samba or NFSv4 with Linux quotas | FSRM |
| Block storage | Microsoft iSCSI Target Server; Linux LIO/targetcli; NFS export; SMB 3 share | iSCSI |
| Remote access | Routing and Remote Access Service (RRAS) with IKEv2; OpenVPN; WireGuard; L2TP over IPsec with a pre-shared key | RRAS, IKEv2 |

#### 5.1.3 Why the named Microsoft technologies were selected

**AD DS as the single directory.** The standard names the technology directly: `Install and manage enterprise directory services (ADDS, LDAP)` (Domain 4, 25 %), and a second line, `Select the roles and/or features of the operating/server system e.g. Active Directory Domain Services (role) and Window Server Back-up (feature)` (Domain 6), makes role/feature selection itself assessed competence. The design uses one forest, one domain and one tree, `vertexpeak.fyp.lab`, at Windows Server 2025 functional level, with two writable domain controllers at HQ (`vpnz-dc01`, `vpnz-dc02`) and a read-only domain controller at Kwun Tong (`vpnz-brdc01`). The RODC is load-bearing rather than decorative: it is the mechanism by which branch authentication survives a wide-area link failure, and it forces the group to reason explicitly about which credentials replicate to a less protected site.

**AD CS for the internal PKI.** The standard names both `Active Directory Certificate Services` and `OpenSSL` under `Setup public key infrastructure services` (Domain 4). AD CS was chosen because it is the only candidate that auto-enrols machine certificates to domain-joined hosts through a Group Policy object, which is what the client's due-diligence requirement for encrypted remote access by certificate, with no shared passwords, demands. The chain is `VP-ROOT-CA` (offline root) issuing `VP-ISSUING-CA-01` (online). If the group concludes in week 7 that a two-tier PKI cannot be operated in the schedule, the documented fallback is a single tier with `vpnz-dc01` issuing directly, and the report must state which model was used.

**FSRM on top of NTFS.** The standard does not contain the string `FSRM`; the justification is the topic sheet plus `Install and manage sharing services` (nested `SMB`, `DFS`, `NFS`, `FTP`) and `Manage file systems` (Domain 4). FSRM is layered on top of, not instead of, NTFS permissions, and the distinction is the point: NTFS and share permissions are an **access-control** mechanism, whereas FSRM is a **policy and accounting** mechanism. FSRM adds four capabilities NTFS cannot express. *Quotas* impose a per-folder capacity ceiling with warning thresholds, which NTFS can approximate only by refusing writes when the volume fills. *File screening* actively denies named file groups — the baseline applies `*.exe;*.vbs;*.mp3` — which is a content-type control rather than an identity control. *Storage reports* produce duplicate-file, large-file, least-recently-accessed and quota-usage evidence, the only mechanism in the design that shows how a share is actually used. *Classification and file-management tasks* allow policy to follow content rather than path. Operationally FSRM answers a question the client's due-diligence list implies without asking: not "who may open this file" but "how large may this department's data grow, what may it contain, and can we demonstrate that policy was enforced?" The baseline implements `D:\Shares\Finance` (20 GB), `Engineering` (10 GB), `SalesRO` (10 GB) and `Public` (5 GB) with the file group `Blocked-Executables`.

**iSCSI for the platform tier.** `iSCSI` is absent from the standard; the bridge is `Manage file systems` (nested `LVM/Dynamic disks`, `Software RAID`) with the topic sheet's explicit naming. The functional reason is that iSCSI presents a *block device* — the initiator sees a raw disk over TCP 3260 and may place any volume layout on it — whereas SMB and NFS present a *file system interface* in which the server owns the volume structure and metadata semantics.

| Property | iSCSI (block over TCP 3260) | SMB 3 / NFS (file over TCP 445 / 2049) |
|---|---|---|
| Unit exposed to the client | A raw LUN; the client chooses NTFS, ReFS or EXT4 | Files and directories on a server-owned volume |
| Client-side file system control | Full — the initiator formats, mounts and manages the volume | None — layout is dictated by the server |
| Device-level multipath / failover | Yes, via MPIO or Linux multipath; a LUN can be re-presented to another host | Session-level failover only |
| Access control | Target-side: initiator IQN allow-list, CHAP secret, plus a network ACL on TCP 3260 | Share and file permissions against Kerberos or LDAP identity |
| Failure mode when the target is lost | The block device disappears and the guest file system becomes unresponsive; continued writes can damage it | The mount becomes stale; typically cleaner at the application layer |
| Design fit here | Platform-tier volumes that must be movable between hosts; 20/40/60 GB thin LUNs on `vpnz-san01` | Not used for the platform tier; SMB serves the ordinary user shares |

Block semantics were selected because the project must demonstrate a storage path independent of the guest's own file-service stack, and because the CHAP-authenticated initiator-target relationship is a concrete least-privilege control with no direct SMB equivalent. The design deliberately does not use MPIO, does not route the LUN beyond VLAN 80, and does not claim Windows failover clustering or Storage Spaces Direct.

**RRAS with IKEv2 for remote access.** Neither `RRAS` nor `IKEv2` appears in the standard. Two bridge lines justify the work: `Install and manage remote network access services` (nested `SSH`, `Remote Desktop Services`) in Domain 4, and `Provide network connectivity between remote branches using VPN technologies such as IPSec, SSL VPN, Direct Access, OpenVPN, DMVPN, GRE, etc.` in Domain 3, which names IPsec directly. RRAS runs on `vpnz-rras01` as an IKEv2 remote-access server with Network Policy Server (NPS) as the RADIUS authorisation authority. IKEv2 supports NAT traversal by encapsulating IPsec ESP in UDP 4500 as well as native UDP 500, and its rekeying and liveness model is why it survives the network changes a travelling laptop experiences; the protocol family is confirmed in RFC 7296, *Internet Key Exchange Protocol Version 2 (IKEv2)*. Two non-default choices are decisions, not defaults. Authentication is **certificate-based only** — machine certificate plus user account — with pre-shared-key IKEv2 forbidden by design, because a pre-shared key is a shared password and the client's requirement excludes shared passwords. And **split tunnelling is disabled**, so all client traffic traverses the tunnel and a single auditable path exists whose routing table can be captured as evidence. NPS requires both a valid machine certificate and membership of `GG-VPN-Users`, which makes authorisation a group-membership fact testable by removing a user and reconnecting.

#### 5.1.4 Alternatives considered and rejected

| Alternative | Reason for rejection |
|---|---|
| **Samba AD DC** | Samba can perform a genuine AD-compatible domain-controller role and is the strongest open-source candidate. It was rejected because the project must demonstrate Group Policy, AD-integrated DNS, AD CS auto-enrolment, FSRM and RRAS IKEv2 — Windows-native role/feature combinations whose GPO, certificate-template and NPS behaviour is only fully verifiable on Windows Server. Samba remains the right answer if licence cost rather than capability were the binding constraint, and the report must say so rather than implying Samba is inferior. |
| **OpenLDAP with a separate Kerberos realm** | Rejected on integration risk. OpenLDAP is a general-purpose directory and is named in the same standard line as AD DS, but it is not a domain controller: no equivalent replication maturity, no Group Policy delivery, no integrated DNS, no native Windows service authentication. Rebuilding those services would consume the schedule without adding assessed competence. |
| **OpenSSL driven directly for the whole PKI** | The standard names `OpenSSL` alongside AD CS, and the design uses OpenSSL primitives indirectly through Easy-RSA on the Linux side. Direct OpenSSL was rejected on the Windows side because it offers no enrolment or renewal automation, no template model and no Group Policy distribution of the trust anchor; managing a dozen host certificates by hand would be less auditable than the automation it replaces. |
| **Samba or NFS with Linux quotas instead of FSRM** | Rejected as the primary mechanism: Linux quota tooling has no equivalent of screening by file group, no storage-report generator and no path to the client-facing reporting the due-diligence narrative requires. The Linux estate still uses `mdadm`, LVM and EXT4 under `Manage file systems`, so the alternative is not unrepresented — it is simply not the answer to the file-policy question. |
| **L2TP/IPsec with a pre-shared key instead of IKEv2 with certificates** | Rejected outright: a pre-shared key is a static shared secret distributed to every client. |
| **NFS or SMB instead of iSCSI** | Rejected for the platform tier as set out above: file-level protocols cannot deliver client-controlled block semantics or initiator-identity access control. |
| **Windows failover clustering, Storage Spaces Direct, Scale-Out File Server** | Rejected and marked **not covered**. One hypervisor host cannot provide a genuinely independent shared-storage path, and nested-virtualisation clustering would produce results that could not honestly be presented as availability engineering. Recorded as future work. |

#### 5.1.5 Security and operational considerations

Least privilege is encoded in groups rather than in individual accounts: `GG-Server-Admins`, `GG-Tier0-Admins`, `GG-Helpdesk` with delegated reset rights on `OU=Users` only, and `GG-Finance-RW`/`GG-Finance-RO` mapped onto the FSRM shares. Two of the four students hold `GG-Tier0-Admins` and are the only accounts permitted to touch `vpnz-dc01`, `vpnz-dc02` or the certificate authority; the others administer member servers, network devices and the DMZ. This tiering is a social and account-level control enforced by group membership and logon-rights policy, not a hardware-enforced privileged-access-workstation boundary, and the report must not present it as more than that.

Operationally, four items dominate. Time is first: Kerberos tolerates less than five minutes of skew, so `vpnz-dc01` is the authoritative time source and a deliberate time-skew fault is a documented troubleshooting scenario. DNS is second: every client is configured with `10.10.30.11` then `10.10.30.12`, and the branch read-only controller is never the only resolver for any client, because a domain whose DNS is unreachable has functionally failed. Capacity is third: FSRM quotas can silently convert an application failure into a disk-full error, so quota thresholds must alert through the monitoring stack rather than be discovered by a user. Backup is fourth and most easily over-claimed: the design covers Windows Server Backup to an iSCSI LUN plus a documented off-host configuration and evidence copy, and it explicitly does not claim a hypervisor-level or full-system backup, because no such licence exists here.

**Selection rationale.** Windows Server was selected because the topic sheet names six Windows-specific capabilities — AD DS, AD CS, FSRM, iSCSI, RRAS and IKEv2 — and because AD DS is one of the few technologies in the whole project that the WSOS 2026 names verbatim in a requirement line, making the choice defensible from both directions at once. FSRM was layered onto NTFS permissions rather than substituted for them because access control and capacity or content policy are different problems, and only FSRM gives the project a quotable enforcement event in the form of a refused write. iSCSI was preferred to SMB or NFS for the platform tier because a block LUN exposes volume control to the client and supports an initiator-identity access model, which is the specific least-privilege behaviour that tier must demonstrate. RRAS with IKEv2 and certificate-only authentication was selected to satisfy the client's prohibition on shared passwords and to make authorisation a group-membership fact that can be evidenced by removal and re-test. Every choice in this line that the standard does not name is presented as a decision justified by the topic sheet and a generic requirement line, never as a WSOS requirement.

### 5.2 Linux Server Administration

#### 5.2.1 State of the art

Linux server administration has moved toward declaratively described estates: a minimal reproducible base image; a firewall expressed as an atomic ruleset rather than a command sequence; availability expressed as a floating virtual address with a service-aware health check; and every configuration file owned by version control. Two further shifts are visible. The reverse proxy has become the standard publication point for web services, so origin servers are no longer exposed and TLS is terminated and re-encrypted at the proxy. And VPN engineering has bifurcated: mature TLS-based tunnels serve interoperable, policy-heavy deployments, while minimal kernel-integrated tunnels have displaced them wherever throughput and configuration simplicity dominate.

#### 5.2.2 Candidate technologies

| Capability required | Candidates considered | Named by the topic sheet |
|---|---|---|
| Web serving and reverse proxying | Nginx; Apache HTTP Server; Microsoft IIS; HAProxy as a pure proxy | Nginx |
| Virtual-address failover | Keepalived (VRRP); DNS round-robin or multiple A records; commercial application delivery controller; cloud load balancer | Keepalived |
| Packet filtering and NAT | nftables; iptables/ip6tables; ufw; firewalld | nftables |
| Remote-access VPN | OpenVPN; WireGuard; strongSwan IPsec; SoftEther | OpenVPN, WireGuard |
| Linux-side PKI | Easy-RSA; OpenSSL directly; step-ca | (not named; selected to support the above) |

#### 5.2.3 Why the named Linux technologies were selected

**Nginx as reverse proxy and web tier.** Nginx is named verbatim: `Install and manage web hosting services using modern web servers e.g. Apache, Nginx and IIS.` (Domain 4) — a line that names all three of the project's web servers, so the comparison below is directly assessable. Nginx was selected for the DMZ front door because its event-driven architecture handles many concurrent, mostly idle connections with modest memory, which is the profile of a TLS-terminating proxy; because an `upstream` block expresses a server pool in a few lines; and because `proxy_pass` with a re-encrypted upstream gives genuine end-to-end TLS rather than a plaintext hop inside the DMZ. Two independent pairs run behind floating addresses: `vpnz-dmzrev01`/`vpnz-dmzrev02` behind VIP 10.10.90.10 with pools `weba_pool` (10.10.90.21:443, 10.10.90.22:443) and `wp_pool` (10.10.90.25:443, 10.10.90.26:443), with Nginx also serving the content nodes `vpnz-dmzwp01`/`vpnz-dmzwp02`.

| Criterion | Nginx | Apache HTTP Server | Microsoft IIS |
|---|---|---|---|
| Process/thread model | Event-driven, asynchronous; one worker per core | Hybrid multi-process/multi-thread; a process or thread per connection in the classic model | Kernel-mode HTTP.sys driver with worker processes |
| Memory under many idle connections | Low and largely flat | Higher; tuning required | Low, but tied closely to the Windows worker-process model |
| Configuration idiom | Declarative `server`/`location` blocks with inheritance | Per-directory `.htaccess` and module directives | GUI plus `applicationHost.config` and `web.config` |
| Reverse proxy and TLS termination | First-class, via `proxy_pass` and `upstream` pools | Strong via `mod_proxy` | Strong via ARR, but not the default deployment idiom |
| Standard's treatment | **Named** in the same requirement line | **Named** in the same requirement line | **Named** in the same requirement line |
| Role in this design | **Front door**: TLS termination, re-encryption, HTTP-to-HTTPS redirect, content hosting | Not deployed | **Deployed** for the DMZ application tier (`vpnz-dmzweba01/02`) |

The design deliberately uses two of the three servers the standard names — Nginx on Linux and IIS on Windows in the DMZ — which lets the report compare them against real configuration rather than in the abstract.

**Keepalived for virtual-address failover.** `Keepalived` is absent from the standard, but the protocol it implements is not: `Provide network load balancing & fault tolerance at routing and switching levels by using GLBP, HSRP, VRRP, LACP, PAgP, etc.` (Domain 3) names **VRRP**. The bridge is strong and must be presented as a bridge: the standard names VRRP, Keepalived is a VRRP implementation. Two independent instances exist — VRID 51 on the nftables pair (VIP 10.10.50.10 on 10.10.50.0/28, nodes 10.10.50.11 and 10.10.50.12) and VRID 61 on the Nginx pair (VIP 10.10.90.10 on 10.10.90.0/24, nodes 10.10.90.28 and 10.10.90.29, so the VIP is owned by no node) — and the identifiers differ deliberately, because reusing one on two segments that could ever be bridged produces two masters and a duplicate-address fault. Both pairs move within a single broadcast domain, so no VRRP-over-tunnel caveat applies.

| Mechanism | How failover is triggered | Strengths | Weaknesses for this design |
|---|---|---|---|
| **Keepalived/VRRP (selected)** | The master advertises at a fixed interval; a backup that misses advertisements promotes itself. A `track_script` can also demote the master when a service check fails | Vendor-neutral; works for any IP service; transitions in sub-second to a few seconds; the health check can be service-aware rather than merely link-aware; one tool serves two different services | Requires a shared Layer-2 segment; VRRP authentication is weak and must be treated as a lab simplification; misconfigured priorities can produce dual masters |
| DNS round-robin or multiple A records | None — DNS returns several addresses and relies on the client trying another | Trivially simple; no extra component; works across segments and sites | No health awareness, so a dead server keeps receiving connections; client retry behaviour is inconsistent and unspecifiable; TTL caching delays withdrawal; produces no failover event to evidence |
| Commercial application delivery controller | Proprietary health monitors plus appliance failover | Rich Layer-7 health monitoring, connection draining and TLS offload at scale | Cost and licence conflict with the no-commercial-licence constraint; adds a black box the group cannot fully document; not required by the brief |
| Cloud load balancer | Provider health checks against managed endpoints | Elastic, with no infrastructure to run | The design is a self-contained lab with no cloud account and no real public addresses; the dependency would break reproducibility |

**nftables for filtering and NAT.** `nftables` is absent from the standard; the bridge is `Apply basic security configuration for control and data plane` (Domain 3) with the Domain 3 know/understand lines `Security protocols to secure local and wide area networks` and `Common types of attacks on network protocols and mitigation methods`. The pair sits *inline* between the HQ core and the ASA, so all traffic from `Z-SERVER` and `Z-USER` toward the Internet passes through a stateful, logging filter that also performs NAT. The single ruleset is `table inet fyp_filter` in `/etc/nftables.conf`, with included fragments under `/etc/nftables.d/` (`10-sets.nft`, `20-filter-input.nft`, `30-filter-forward.nft`, `40-nat.nft`, `90-logging.nft`) that are `include`d rather than independently loaded, because nftables is one atomic ruleset and loading fragments separately would create transient states with no policy.

| Firewall tool | Underlying mechanism | Configuration model | Verdict |
|---|---|---|---|
| **nftables (selected)** | A single kernel ruleset with named tables, chains, sets, maps and verdicts | One atomic file, loadable transactionally; native sets make peer-group matching efficient; per-rule logging prefixes | Selected: atomic apply, sets for the trust-zone peer groups, `log prefix "NFT-DROP: "` on every drop rule, and a documented rollback timer |
| iptables/ip6tables | Independent per-table chains in the legacy kernel interface | Long imperative command sequences; rules live as an ordered list with no atomic source of truth unless `iptables-save` is used | Rejected as primary: no single declarative artefact to version, and IPv4/IPv6 handling is duplicated |
| ufw | A simplified front end over the legacy netfilter interface | Very short, opinionated commands | Rejected for a router-style inline pair: the abstraction cannot express the forwarding, NAT and set-matching policy required, and it hides the ruleset from the audit trail |
| firewalld | Zones and services over the netfilter back end | Declarative zone model with runtime and permanent configuration split | Rejected: the zone abstraction is attractive, but policy is already expressed as explicit zone objects and `ACL-{ZONE}-{DIR}-{NN}` naming, and a second, parallel zone vocabulary would invite inconsistency |

Three operational controls accompany the choice. The ruleset is applied by `02-nftables-apply.sh`, which arms a revert timer so a bad ruleset cannot lock administrators out of a remotely managed virtual machine — the lockout risk is documented and the mitigation is demonstrated, because that failure mode is the classic consequence of remote firewall work. The pair's configuration is collected, versioned and diffed, so out-of-band change becomes visible. And the management tunnel on UDP 51820 between `vpnz-nft01` and `vpnz-mon01` is documented as an out-of-band escape hatch whose absence must be evidenced during the security test, so the escape hatch cannot become an undocumented back door.

**OpenVPN and WireGuard together.** `OpenVPN` is named verbatim in the standard: `Provide network connectivity between remote branches using VPN technologies such as IPSec, SSL VPN, Direct Access, OpenVPN, DMVPN, GRE, etc.` (Domain 3). `WireGuard` is not named; the only licence the standard gives is the `etc.` at the end of that line, making it the **weakest bridge in the project**, and the report must say so in those terms.

| Criterion | OpenVPN 2.6.x | WireGuard (`wireguard-tools` 1.0.20210914) |
|---|---|---|
| Cryptographic design | TLS-based; negotiates a cipher suite; typically X.509 certificate authentication with a private CA and a revocation list | A fixed modern primitive set — Curve25519 for key agreement, ChaCha20-Poly1305 for authenticated encryption, BLAKE2s for hashing — with no negotiation and therefore no downgrade surface |
| Attack surface and code size | Large codebase with many options and a plug-in mechanism; user-space | Deliberately small, kernel-integrated codebase with a very narrow configuration surface |
| Performance | Lower throughput and higher per-packet cost from user-space copies and TLS record handling | Substantially higher throughput and lower latency at equal CPU cost, because of the kernel data path and simpler protocol |
| Transport and traversal | UDP or TCP, including TCP 443, which is valuable where UDP is blocked or shaped | UDP only; a network that drops UDP breaks it outright |
| Roaming and NAT | Reconnect logic and `float` behaviour handle address changes | Roaming is intrinsic — a peer's observed source address updates the session without renegotiation, which is why `PersistentKeepalive` is needed only on the client side |
| Identity and revocation | X.509 identity with a certificate revocation list; per-client configuration directories allow per-user policy | A raw public key per peer; revocation means removing the peer entry, with no revocation-list equivalent and no per-user identity unless another mechanism supplies one |
| Operational maturity | Very long deployment history, extensive documentation, broad interoperability | Newer, smaller, rapidly adopted; historically labelled an experimental implementation; still weaker in enterprise policy features |
| Role in this design | Second, independent remote-access implementation on `vpnz-lnxra01` with Easy-RSA PKI, per-client `ccd`, `tls-crypt` preferred over `tls-auth`, `duplicate-cn` disabled and a documented revocation test | Primary small-office tunnel (`WG-HQ-WC`) and the remote-worker pool on the nftables VIP; keys generated with `wg genkey` and never committed; `AllowedIPs` restricted to the exact prefixes required, never `0.0.0.0/0` on a site-to-site peer |

Both are used deliberately, for three reasons. The first is defensibility: running the two tunnels side by side converts a comparative statement into measured evidence — a handshake capture, a throughput comparison and a CPU-cost comparison taken on the group's own hardware. The second is cryptographic diversity at the perimeter, so a defect in one protocol family does not disable remote access. The third is functional fit: WireGuard's kernel path and roaming suit the site-to-site and always-on cases, while OpenVPN's PKI, per-client policy, revocation and TCP transport suit a staff member behind a network that blocks UDP, or an organisation that needs certificate-level revocation semantics. One compromise must be stated: WireGuard is placed on **UDP 443**, a port commonly permitted outbound, which is a pragmatic reachability choice rather than a security control, and the coexistence of WireGuard on UDP 443, IKEv2 on UDP 500/4500 and OpenVPN on UDP 1194 behind one published address means the demultiplexing rules on the pair are themselves security-relevant configuration requiring review.

Easy-RSA 3.1.x on `vpnz-lnxra01` was selected as the Linux-side authority because the standard names `OpenSSL` under `Setup public key infrastructure services` and Easy-RSA is a structured workflow over OpenSSL primitives rather than a different cryptography stack; the report must state that the project uses Easy-RSA rather than driving OpenSSL directly, because that is a real difference between what the standard names and what the project operates.

#### 5.2.4 Security and operational considerations

The Linux estate is hardened from one baseline (`01-hardening-baseline.sh`). Root login is prohibited; password authentication is disabled for Linux-to-Linux access in favour of Ed25519 keys; and authorisation is restricted to the group `gg-infra-admins`, whose membership mirrors the four named administrators so that both platforms share identical administrative identities. Address-family policy is default-deny in both directions on the inline pair, with explicit `ct state established,related accept` and a logging prefix before every drop. AppArmor is left at distribution defaults and the report must say so rather than implying that custom mandatory-access-control policy was authored. Two operational risks are inherent to this line and carried in the risk register: a remote firewall change can remove administrative access, mitigated by the revert-timer script; and a VPN key committed to version control is a permanent compromise, mitigated by `.gitignore` entries for `*.key`, `wg*.conf`, `*.pem`, `*.pfx` and `pki/`, by mode 0600 on `/etc/wireguard/wg0.conf`, by an Ansible Vault, and by a pre-release credential sweep whose output is retained as evidence. The pair's VRRP `auth_type PASS` is a lab simplification on a host-only segment and must be described as such, not as best practice.

| Design element | WSOS domain served | Basis |
|---|---|---|
| Nginx reverse proxy, TLS termination, upstream pools, content nodes | 4 Network and System Operations (25 %) | **Named**: `Install and manage web hosting services using modern web servers e.g. Apache, Nginx and IIS.` |

Keepalived was selected because it implements VRRP, which the standard names, making it the one component in this line whose standard linkage is a named protocol rather than an inference, and because a health-check-driven virtual address produces an observable failover that DNS round-robin cannot. nftables was preferred to iptables, ufw and firewalld because its atomic single-ruleset model gives the project one declarative artefact to version, review and roll back, which is the property the client's audited-change requirement actually needs. Where the standard is silent, each choice is presented as a bridge quoting the requirement line the inference rests on.

### 5.3 Cisco Networking

#### 5.3.1 State of the art

Enterprise routing and switching rests on a few stable ideas. Inside an autonomous system a link-state interior gateway protocol is used almost everywhere, because a topology map gives fast loop-free convergence and a predictable cost metric; where legacy Cisco estates exist, a proprietary interior protocol often persists because migration costs more than it gains. At the boundary an exterior gateway protocol carries policy rather than topology. In the access layer the spanning-tree family remains the loop-prevention mechanism of record, with the older algorithm almost entirely displaced by its rapid successor. At the perimeter the stateless access control list has been displaced by the stateful, zone-aware appliance.

#### 5.3.2 Why the named Cisco technologies were selected

This is the best-covered line of the five. The standard names all three routing protocols in one sentence, which is the strongest single citation available to the project:

> `Provide enterprise-wide connectivity using internal and external gateway routing protocols such as OSPF, BGP and EIGRP` (Domain 3, Data Transfer Networks, 25 %)

**OSPF as the interior gateway protocol.** Open Shortest Path First is a link-state protocol: each router floods link-state advertisements, every router builds an identical topology database for its area, and each computes shortest paths with the Dijkstra algorithm. The design runs a **single area 0** across HQ and Kwun Tong, with authentication on core links, passive interfaces wherever no neighbour can legitimately form, and `default-information originate` at the HQ edge so interior routers receive a default rather than a full external table. A single area was chosen over a multi-area design deliberately: multi-area tuning — area ranges, stub and not-so-stubby areas, virtual links — adds real complexity and real failure modes, and the assessed value lies in building, breaking and repairing one working domain rather than in hierarchy theory that a 12-week schedule cannot verify. OSPF advanced features beyond one area, OSPFv3 and MPLS are not covered.

**EIGRP where the scenario justifies it.** Enhanced Interior Gateway Routing Protocol is a Cisco-proprietary advanced distance-vector protocol that combines a neighbour-relationship model with a diffusing computation to guarantee loop-free paths, carrying a composite metric of bandwidth and delay with reliable transport of its own updates. Its merits and its lock-in are the same fact: efficient and fast inside a single-vendor domain, restrictive of vendor choice. EIGRP is justified here on the scenario's own terms. The narrative contains a legacy acquisition — the Macau representative office and one transit segment inherited with the acquired professional-services business — already running EIGRP as autonomous system 100. Replacing it would mean re-addressing and re-designing a working segment for no functional gain while the integration proceeds; the correct engineering answer is to run EIGRP at the boundary of that domain, redistribute once, and plan the migration as future work. Two honesty constraints apply: EIGRP is demonstrated in **classic mode** only, and its presence must not be presented as a recommendation that a new network should adopt a proprietary protocol.

**BGP at the edge.** The distinction between an interior and an exterior gateway protocol is the heart of this section. An IGP answers *where is the destination inside my own network*: it distributes internal topology and has no concept of policy, ownership or trust. An EGP answers *which external networks should I reach, through which neighbour, and on what terms*: it distributes reachability between autonomous systems that do not share administrative control, and it carries the attributes with which operators express preference, filtering and traffic engineering. The two do not compete. Vertex Peak is autonomous system 65001, peering with the primary provider (65000) and, as a secondary session, an alternate provider (65002); Wan Chai is modelled as a small autonomous system 65021. The designed demonstrations are inbound prefix filtering with a prefix list, outbound route-map prepending, local preference to prefer the primary path, `maximum-prefix` protection, and a captured failover when the primary session is shut down. The declared ceiling must be stated: Packet Tracer's BGP support is basic, and route reflectors, confederations, `add-path`, RPKI and BGPsec validation are outside what the simulator models faithfully and are therefore not claimed.

**RSTP instead of STP.** The exact string `RSTP` does not occur in the standard; the legitimate hook is `Configure access, aggregation and core level switching` (Domain 3). The reference standard to cite by title is **IEEE 802.1w**, *Rapid Reconfiguration of Spanning Tree*, subsequently folded into the IEEE 802.1D-2004 revision, so the edition actually consulted must be recorded rather than a clause number invented. The design's topology — two core switches joined by a trunk with four dual-homed access switches — is precisely the arrangement that requires loop prevention and benefits from fast convergence.

| Property | STP (IEEE 802.1D, original) | RSTP (IEEE 802.1w) |
|---|---|---|
| Convergence mechanism | Timers: a blocking port must age out before it can forward, so convergence is timer-bounded | Explicit **proposal/agreement** handshake on point-to-point links; edge ports forward immediately; a new root port can forward without waiting for timer expiry |
| Port roles | Root, designated, blocked | Root, designated, **alternate** and **backup**, so an already-known alternate path is available without re-computation |
| Topology-change propagation | The notification is flooded to the root and then outward, and propagates slowly | Changes are propagated immediately from the detecting bridge to all others, and stale-entry flushing is scoped rather than global |
| Behaviour on a failed root port | The port moves through listening and learning with timer delays | The alternate root port is promoted without delay in the common case |
| Consequence here | A link pull can interrupt traffic for tens of seconds, long enough to break DHCP, Kerberos or a management session | Interruption is greatly reduced, which matters because management and identity traffic crosses the same access layer |
| Protection features | None of the below | Root guard, BPDU guard, loop guard and edge-port configuration contain failure modes instead of merely recovering from them |

RSTP's advantage here is not merely speed: the port roles make the topology auditable, because the report can name the root bridge, the secondary root and each port's role and state, and then demonstrate that pulling a link produces the expected role change. Root selection is therefore explicit rather than elected — `VP-HQ-CORE-01` as root primary for the traffic-carrying VLANs and `VP-HQ-CORE-02` as root secondary, `portfast` with `bpduguard` on access ports, root guard on expected root ports. The convergence demonstration uses Packet Tracer's simulation mode and `show spanning-tree detail` timestamps, and **any timing measured in Packet Tracer is a simulation artefact that must be labelled as such**, never presented as a real-world convergence figure.

**The ASA as a distinct firewall tier from router ACLs.** The string `ASA` does not occur in the standard; the bridges are `Apply basic security configuration for control and data plane` and the Domain 3 VPN line. The design places an ASA 5506-X device (`VP-HQ-FW-01`, ASA 9.16(4) image in Packet Tracer) at the DMZ and edge, with security levels outside 0, dmz 50 and inside 100. The architectural point is that an ASA is not a faster router ACL, and the two belong in different places.

| Property | Router ACL | Firewall appliance (ASA) |
|---|---|---|
| State | Stateless: each packet is matched in isolation against an ordered list | Stateful: a connection table tracks established flows, so return traffic is permitted by state rather than by a mirrored rule |
| Match sophistication | Source, destination, protocol and port with wildcard masks | The same plus object groups, security levels, application inspection engines and zone-derived implicit rules |
| Position in a topology | An optimisation and containment tool applied per interface on the routed path | A trust boundary: a dedicated device whose purpose is to separate zones and hold inspection and logging policy |
| Address translation | Not its role | NAT and PAT are first-class and configured next to policy rather than elsewhere |
| Payload awareness | Cannot alter payload or embedded addresses | Inspection can open pinholes for protocols carrying addresses inside the payload, such as FTP or SIP |
| Use in this design | Management-plane restriction, anti-spoofing and containment of the isolated lab segment | The DMZ boundary, inside-to-outside policy, NAT, and the site-to-site IPsec tunnel to Wan Chai |

Router ACLs remain — they are how the management plane is protected and how the student segment is contained — but they sit at the *containment* layer while the ASA sits at the *trust-boundary* layer. The declared limitation must appear in the report: Packet Tracer's ASA is a reduced legacy-ASA model, and FirePOWER/SFR, clustering, active/standby failover with state replication, `shun` and much low-level drop instrumentation are absent or incomplete, so **no ASA high-availability, clustering or next-generation-firewall capability may be claimed.**

#### 5.3.4 Security and operational considerations

Spanning tree is a control-plane protocol with no native authentication, and an attacker who injects superior BPDUs can become root and black-hole traffic; the mitigations are root guard on expected root ports, BPDU guard on access ports, and an isolated `Z-STUDENT` segment denied everything except its own subnet and a single console path. DHCP is similarly trust-sensitive: snooping is enabled with trusted ports restricted to the core uplinks, and a rogue-DHCP test is captured and shown to be blocked. On the routing side, OSPF authentication protects adjacencies, `maximum-prefix` bounds the damage a misbehaving peer can do, and inbound prefix filtering prevents the provider from injecting a default route or an unexpected prefix set. The most dangerous operational fact in this line is that **mutual, un-tagged redistribution between OSPF and EIGRP can create a routing loop that is invisible in the configuration and visible only in the forwarding table**, which is why the project deliberately misconfigures this once, captures the loop and then fixes it.

A second consideration is the honest boundary of the simulator. Because Packet Tracer has no SSH server reachable from external tooling and no API, no automation software ever logs in to a Packet Tracer device. Network-device automation is therefore delivered as a documented two-track approach in which the intended device configurations live as text files in version control and the collection mechanisms are tested against the Linux and Windows estate. The report must state plainly that **no playbook ever logged in to a Packet Tracer device**; claiming otherwise would be fabrication.

### 5.4 Network Automation

#### 5.4.1 State of the art

Infrastructure operations has moved from a runbook executed by hand to a repository executed by a tool. The prevailing model is *infrastructure as code*: intended state is declared in a version-controlled artefact, a tool converges the live system toward it, and the difference between the two becomes the reviewable unit of change. Three supporting practices sit around it — version control with peer review, secret management separated from configuration, and a log for every run. The shift is about auditability rather than speed: a hand-typed change leaves no artefact to review, whereas a declarative change leaves a diff, a reviewer's name and a run log.

#### 5.4.2 Imperative scripting compared with declarative configuration management

The technologies named by this line sit on both sides of the imperative/declarative divide, and the design uses both deliberately.

| Dimension | Imperative scripting (PowerShell, Bash) | Declarative configuration management (Ansible) |
|---|---|---|
| What the artefact expresses | A sequence of steps and decisions: "check this, then set that, then restart" | A desired end state: "this package is present, this file has this content, this service is running" |
| Who decides what to change | The author, at write time; logic is embedded in control flow | The tool, at run time, by comparing observed state with declared state |
| Re-run behaviour | Depends on the author: without guard conditions a script reapplies its effects | Idempotent by design for well-chosen modules: a second run reports no change |
| Failure and partial application | Mid-script failure leaves an arbitrary intermediate state unless the author handles it | The task fails at a known point; converged tasks remain converged, so re-running resumes rather than repeats |
| Reviewability | A diff of code, whose *effect* a reviewer must infer | A diff of intent, largely legible to a reviewer |
| Suitability | Ad-hoc queries, reports, one-off remediation, collection — anything genuinely procedural or conditional | Baseline configuration, service deployment, repeated state across many hosts |
| Evidence produced | Whatever the author logs | A per-task `ok`/`changed`/`failed` record per host, directly quotable as evidence |

Idempotence is what makes declarative tooling auditable, and its importance here is concrete. The client's due-diligence item is *"evidence that network change is applied through reviewed, repeatable configuration rather than by hand."* A converged second run — a playbook execution reporting zero changed tasks — is the cleanest proof that the configuration is in the declared state and that running again will not perturb a working system. That is why idempotence is a hard acceptance criterion: every playbook is run twice and the second run's `changed=0` result captured. Imperative scripts are held to the same standard by requiring each to be re-runnable with unchanged output.

#### 5.4.3 Why the named technologies were selected

**Ansible for configuration management.** The standard makes this the least ambiguous requirement in Domain 5: `Identify and implement infrastructure as code` with the nested example `Ansible.` — a *shall be able to* requirement, not a know/understand one. The topic sheet says "Ansible Playbook"; the standard says only `Ansible`, and the report should make that distinction explicit and then state that playbooks are the implementation form.

| Criterion | Ansible (selected) | Puppet | Chef | Salt |
|---|---|---|---|---|
| Execution model | Agentless, push-based: connects over SSH (Linux) or WinRM (Windows), copies a module, executes, removes it | Agent-based pull: each node runs an agent that fetches a catalogue from a master on a schedule | Agent-based pull, with a central server holding cookbooks | Both agent-based with a master, and agentless `salt-ssh` |
| Authoring language | YAML task lists plus Jinja2 templates — no new general-purpose language | Puppet's own declarative DSL | Ruby, embedded in recipes | YAML with Jinja2, comparable to Ansible |
| Sequencing | Ordered task execution with handlers, which suits "configure, verify, then restart" | Dependency-graph ordering; order is derived rather than written | Recipe and resource order with explicit notifications | Ordered state files |
| Extra infrastructure | **None** — no agent, no agent certificates, no master to keep available | A master plus agent certificates | A Chef Infra Server plus agent keys | A master plus keys |
| Fit to this estate | Manages **both** the Linux estate over SSH and the Windows estate over WinRM from `vpnz-mon01` | Strong on Linux; less idiomatic for this Windows role/feature model | Strong, but Ruby cookbook development is a disproportionate skill cost in 12 weeks | Comparable, but with fewer Windows-specific modules |
| Fit to the standard | **Named verbatim** in a *shall be able to* requirement | Not named | Not named | Not named |

Ansible was therefore selected on four converging grounds: the standard names it as a requirement; it is agentless, removing an entire class of infrastructure (agents, agent certificates, a master's availability) that a single-host lab would otherwise have to build and defend; its YAML task model is learnable fast enough to be productive within the schedule; and it manages the heterogeneous Windows-and-Linux estate from one control node. The control node is `vpnz-mon01` and nothing else — **no playbook is ever run from a student laptop**, so the version stays pinned and the evidence reproducible.

**PowerShell for the Windows and Active Directory side.** PowerShell is named verbatim twice: as a nested scripting language under `Setup and run routine infrastructure maintenance operations using various scripting\programming languages` (Domain 5) and within `Script based backup, e.g. Bash, Batch or PowerShell` (Domain 4). What it brings is not merely a scripting language but structured, object-oriented access to the operating system's own management surface. Every role and feature used here exposes a module with verb-shaped cmdlets returning objects rather than formatted text: `Get-ADUser`, `Get-ADReplicationFailure`, `Get-DhcpServerv4Scope`, `Get-FsrmQuota`, `Get-IscsiSession`, `Get-VpnConnection`, `Get-Gpo`, `Get-WinEvent`. Three consequences follow. Results can be filtered, compared and exported without parsing, so a health report is a pipeline over objects that can emit CSV, HTML or a test assertion. PowerShell is the *native* interface for AD DS, AD CS, DHCP, DNS, FSRM, iSCSI and Group Policy, so no wrapper is needed. And the same runtime is available over WinRM, which is the transport Ansible uses to reach Windows, so the manual and automated paths use the same language and modules. The five scripts cover new-starter onboarding, AD health reporting, network-device configuration backup, service-endpoint testing (the port matrix as an executable test) and Group Policy backup. The estate runs in-box **Windows PowerShell 5.1** on the guests for scripts that execute there, with **PowerShell 7.4 LTS** on `vpnz-jump01` for authoring; the report must state which runtime each script was actually tested on and must not claim 7.4 where only 5.1 was used.

**Bash for the Linux side.** Bash is named in the same nested position. What it brings is the opposite of PowerShell's structured richness: it is the *composition* language of the Linux estate, in which text streams and exit codes are the native interface of `systemctl`, `nft`, `ip`, `journalctl`, `openssl`, `rsync` and `curl`, and `set -euo pipefail` supplies fail-fast semantics in a single line. The five scripts — hardening baseline, atomic nftables apply with a rollback timer, Keepalived state verification and failover test, restic backup, and certificate expiry and renewal — are all cases where the correct action is a short procedural sequence with a small decision tree. The division of labour is therefore explicit: **Bash and PowerShell handle procedural, conditional, one-off and reporting work; Ansible handles the repeatedly applied, multi-host, declarative baseline.** Where a script must be re-run it is written to be idempotent, and where it mutates a service it uses a templated configuration under Ansible's control rather than editing files in place.

**Git as the substrate.** Git is named verbatim under `Use modern automation tools for systems deployment and configuration management`, and `Importance of code version control` is a Domain 5 know/understand line. The standard also contains `Continuous integration and continuous delivery\deployment pipelines concepts` as a know/understand line, and here an honest proposal must be careful: the project runs a Git review-and-tag workflow and documents the concept, but it does **not** build a pipeline, and the report must say exactly that rather than listing CI/CD as delivered. Likewise Python, YANG, RESTCONF and NETCONF were **removed from Domain 5 in the 2026 edition** — they were present in 2024 — and must not be cited as standard requirements; they may appear only as future work.

#### 5.4.5 Security and operational considerations

Credential handling is the dominant risk. Ansible to Windows uses WinRM over HTTPS on port 5986 with an internal-CA-signed certificate, authenticated by `svc_ansible`, a member of `GG-WINRM-Admins` and of nothing else. Ansible to Linux uses Ed25519 keys whose public halves are stored in the repository and whose private halves are never committed. Any stored secret lives in an Ansible Vault with one vault password held by the group, and a repository-wide credential sweep runs before every tagged release with its output retained. The deliberate test that a fake key committed to the repository is caught by the sweep is itself a test case, because a control that has never been shown to fire is not a verified control.

Three further disciplines matter. The *run log* is the evidence artefact: every script and playbook writes a timestamped log into the repository, commits it, and the verification chapter cites those logs by filename. The *review* control is social as well as technical: every change is reviewed by a second member and the review recorded in the meeting minutes, because the client's requirement is for a *process*, not merely a tool. And the *boundary* must be stated: an automation control node is itself a high-value target, since compromising it yields credentials for the entire estate. `vpnz-mon01` holds the vault, the control node, the Git server and the monitoring stack, which concentrates risk by design; the compensating controls are its placement in `Z-SERVER`, management access restricted to `Z-MGMT`, and an explicit acknowledgement in the risk register that a compromise of this single host would be the most damaging single failure in the environment.

### 5.5 AI Network Management

#### 5.5.1 State of the art

Network operations tooling has passed through three generations. The first was *collection*: protocols and agents reporting counters, thresholds and traps to a central server. The second was *correlation and visualisation*: dashboards and rule-based alerting that raise an alert when a metric crosses a static threshold. The third, current frontier is *agency*: a system is given a set of bounded tools exposing the same underlying data and is asked to gather its own context, correlate signals across sources and produce a conclusion with the evidence attached. The difference between the second and third generations is not the data but who performs the multi-step investigation: threshold alerting compresses a situation into one number and loses the context, which a human then re-expands by opening several consoles, whereas an agent performs that expansion in one pass and returns a narrative with the observations still attached. Where threshold alerting is strong, such as a resource ceiling, it should be kept; where a fault's single symptom appears in three systems, an agent has a genuine advantage.

#### 5.5.2 What an agent plus a "Skill" plugin model means

An *agentic* system in this sense has four properties distinguishing it from a chatbot. It is **tool-using**: its capabilities are discrete callable functions with typed parameters and results, not free conversation. It is **iterative**: it can observe a result, decide it is insufficient, and call another tool within a budget. It is **goal-directed**: it is given an objective such as "triage this alert" rather than a question. And it is **constrained by construction**: the set of tools it may call is finite, enumerated and declared in advance, which is what makes its behaviour auditable and its blast radius definable. A "Skill" is the packaging of one such capability: a manifest declaring the tool's name, purpose, parameter schema and implementing code path. In this design the surface is deliberately tiny — four read-only tools on `vpnz-ai01`.

| Skill manifest | What it reads | Source |
|---|---|---|
| `alert-triage` (`get_active_alerts`) | The current alert set and its metadata | Alertmanager API over HTTPS |
| `interface-health` (`get_interface_stats`) | Interface counters and error rates | SNMPv3 poll of the Packet Tracer device estate; `ip -s link` on Linux |
| `auth-failure-report` (`get_auth_failures`) | Failed-login events | Windows Security event 4625; `journalctl` for `sshd` over SSH |
| `doc-draft` (`draft_change_proposal`) | Nothing external — it writes text only, into `/opt/openclaw/proposals/`, never to a device | Local filesystem |

The architectural significance is that the surface is closed: **there is no fifth tool**, and there is no shell on `vpnz-ai01` through which a device can be reached except along these four read-only code paths. The manifests under `/opt/openclaw/skills/`, the allow-list, the prompt set and sample outputs are all evidence to be retained. Because a Skill model is a *plugin* model, the extension process is what needs governing: adding a fifth tool is a design change that must be reviewed, recorded in the decision log and re-verified. The tool definitions are framed so that they would be expressible as Model Context Protocol (MCP) tool definitions, keeping the surface portable across runtimes — a design choice, not a verified implementation, since the report must cite the specification the group actually reads, and `MCP` occurs zero times in the WSOS 2026.

#### 5.5.3 A constrained tool-calling agent compared with a general-purpose LLM assistant

| Dimension | General-purpose LLM assistant | Constrained tool-calling agent (this design) |
|---|---|---|
| Input | Arbitrary prompts, including pasted configuration and logs | A fixed trigger (an Alertmanager webhook or a schedule) plus a declared tool schema |
| Capability | Produces text; a human transcribes any action by hand | Executes a bounded set of operations and reads their results |
| Effect on the environment | None directly, but an unverified recommendation may be transcribed into a change without review | Only the effect permitted by the declared tools; four read-only tools means no write path exists |
| Evidence of what happened | A conversation, which may not be retained or attributable | A JSON-lines audit record per invocation with a prompt hash and the tools called |
| Risk profile | Concentrated in human transcription of plausible-sounding advice, which is unauditable | Concentrated in the tool surface, which is enumerable and reviewable |
| Suitability for operations | Useful as an interactive aid to a human already investigating | Suitable for a defined, repetitive triage task with a measurable success criterion |

The design takes the constrained-agent position as an architectural commitment, because **the tool surface is the security boundary, and a boundary that can be enumerated can be reviewed.** An assistant whose only output is prose cannot be tested, because there is no specification to test it against. An agent whose capabilities are four declared read-only functions can be tested like anything else here: call each tool, confirm the expected data, confirm no other call succeeds, and confirm no write is possible.

#### 5.5.4 Risk: a careful treatment

Agentic operations carry risks qualitatively different from those of ordinary tooling, because the failure mode is a plausible, fluent, wrong answer delivered with the same confidence as a correct one. Five risks dominate, each with a specific mitigation rather than a general reassurance.

**Hallucination and confabulation.** A language model can produce fluent statements unsupported by the data it read, including invented interface names, counts and causal claims. Mitigations: every output must cite the tool result it rests on; the agent must state what it could not determine; the tools return raw structured data a reviewer can re-check in seconds; and the acceptance criteria **require** that a hallucination or false positive, if it occurs, is documented honestly with the prompt that caused it. Documenting a failure is a stronger academic result than hiding one, and it is the only way to characterise a tool whose behaviour cannot be reasoned about from first principles.

**Blast radius.** An agent that can act can act wrongly at machine speed and scale. The mitigation is architectural rather than procedural: **the agent has no write path at all.** It cannot modify a device, service, rule or directory object, because no tool exposes such an operation and no credential it holds permits one. Its service account `svc_aiagent` is a member of `GG-AI-ReadOnly` only, and that group is granted event-log read access and nothing else. Its only output side effect is writing a *proposed* diff as text. Excluding autonomous remediation is a deliberate design decision with a specific justification: unsupervised remediation would make the project's own verification results irreproducible, because the state under test would change underneath the test.

**Permissions and credential scope.** A read-only credential is still a credential, and the aggregate read surface of a monitoring account is sensitive. The agent holds exactly one account, that account is a member of exactly one group, and the group's grants are documented; no device credential other than that account may be stored on `vpnz-ai01`; and the host's segment placement restricts it to the management and monitoring ports in the port matrix, so a compromised agent cannot become a general-purpose internal foothold.

**Auditability.** A tool whose actions cannot be reconstructed is unusable in a regulated environment, which is the scenario here. Every invocation is logged to `/opt/openclaw/logs/agent.jsonl` with a prompt hash and the calls made, and a hard rate limit on tool calls bounds cost and prevents a runaway loop becoming a denial of service against the monitoring API. The log format is machine-readable so the audit trail can itself be queried.

**Human-in-the-loop.** Every output is labelled **"proposed — requires human approval"** and the workflow terminates at a person. The objective is explicitly *mean-time-to-triage reduction*, not autonomy: the metric improved is how long it takes a person to understand what is happening, and the agent's contribution is to have gathered and correlated the evidence before the person arrives. Two further guardrails follow. False-positive tolerance is asymmetric — a missed alert is worse than a noisy one — so the agent may propose more investigations than a human would initiate, but it may never suppress an alert. And the acceptance criteria require a written evaluation of **where the agent helped, where it wasted time, and where a human was strictly required**, because a proof of concept reporting only its successes has not characterised the tool.

**Honest statement of coverage.** The WSOS 2026 contains **zero** AI content. The strings `Agentic`, `OpenClaw`, `MCP`, `artificial intelligence` and `machine learning` each occur zero times in the 2026 text and zero times in the raw HTML. A naive search for `AI` returns four hits, all substring false positives — `ShanghAI`, `dAIly`, `mAIntain`, `domAIn` — which must never be presented as evidence of coverage. This line is therefore **innovation beyond the standard**, anchored only on general professional attributes it legitimately satisfies: `The speed of IT systems change and the need to maintain currency`, `Use thorough and efficient research methods to support knowledge growth` and `Be enthusiastic to try new methods, systems, and embrace change` (all Domain 1, 5 %). Those are general attributes, not AI coverage, and the report must say so in that order.

**Honest statement of uncertainty.** OpenClaw is the least verifiable component in the project: its installation method, Skill file format, default ports, licence and stable version could not be confirmed at design time. Three consequences follow. No version, URL, licence or capability claim may appear in the report without a screenshot of the running instance in this lab and a citation to the documentation actually used. The AI chapter must open by stating the uncertainty and the fallback taken. And a timeboxed feasibility spike in weeks 5–6 — a maximum of three working days — must produce a *decision*: adopt OpenClaw, adopt the group's own generic agent loop, or drop to a deterministic correlation engine. The fallback ladder is designed in advance rather than improvised: if OpenClaw cannot be installed, the identical four-tool surface is driven by a small generic agent loop and the chapter becomes an evaluation of agentic tooling against the OpenClaw Skills model as a design reference; if no model access exists at all, the deterministic half — the four collectors, the correlation rules and the report generator — is demonstrated with a scripted policy in place of the model, and the substitution is documented. Any of these outcomes produces a defensible result; none permits a claim that was not demonstrated.

## 6. System Architecture Design

### 6.1 Design Principles

Eight principles govern the architecture. They are stated first because every later decision in this chapter is a consequence of one or more of them, and because a decision that cannot be traced to a principle needs re-examination.

**Defence in depth.** No single control is trusted to be sufficient. Traffic leaves the internal network through a stateful nftables filter pair and *then* through a stateful ASA, so the failure of one policy layer does not remove the boundary and a rule mistaken in one language is unlikely to be identically mistaken in the other. This is why the pair sits inline between the HQ core and the ASA rather than beside it: the two-firewall design is a deliberate second application of policy at a second layer, not accidental duplication. The same principle applies at the host layer, where each Linux guest carries its own firewall, and at the identity layer, where Tier-0 and Tier-1 administrative authority are separated.

**Least privilege.** Every identity holds the minimum authority its function requires, and authority is granted to groups rather than accounts. `svc_ansible` is a member of `GG-WINRM-Admins` and of nothing else; `svc_aiagent` is a member of `GG-AI-ReadOnly` and never of Domain Admins; `svc_monitoring` holds performance-counter read only; `svc_ldapbind` exists solely so the DMZ content tier can perform an LDAP bind. Human administrators have named personal accounts (`adm-{initials}`), never shared accounts; only two of the four are in `GG-Tier0-Admins` and only those two may authenticate to the domain controllers or the certificate authority. The break-glass account `da-vertexpeak` exists, is sealed, and any use must be recorded in the report.

**Segmentation.** Trust is expressed as zones on distinct Layer-3 segments rather than as one flat network with host firewalls. HQ alone has a core transit VLAN, a management VLAN, two server VLANs, a user VLAN, a voice VLAN, an egress transit VLAN, an isolated lab VLAN, a storage VLAN and a DMZ VLAN; each branch has its own user, voice and management segments. Where a boundary matters most the segment is also separated at the hypervisor: management lives in `10.20.0.0/16`, deliberately outside `10.10.0.0/16`, so a routing mistake cannot expose the management plane. The honest limitation is recorded: for the real virtual machines a "VLAN" is a separate host-only virtual network, so the *segmentation outcome* is genuine while the *802.1Q mechanism* is emulated.

**Defence of the management plane.** The management plane is the highest-value target in any infrastructure and the least recoverable to lose, because an attacker who holds it can undo every other control. It is therefore treated as the most restricted zone, not the most convenient. Network devices are managed on dedicated addresses in VLAN 20 and, at Kwun Tong, VLAN 113; administrative access is permitted only from `Z-MGMT` and only for named management protocols; every zone may send only syslog and SNMPv3 toward management; and weakly authenticated management is forbidden outright, which is why SNMPv2c and community strings appear nowhere in the design. Remote-access users are never administrators of infrastructure.

**Standardisation and idempotency.** Every Windows guest except the domain controllers is a full clone of `W2K25-TEMPLATE-01` and every Ubuntu guest of `UBU2404-TEMPLATE-01`, so a difference between two hosts is a decision rather than an accident. Above the base image, configuration is applied by playbooks and scripts required to be idempotent: re-running them must not change a converged system, and the second run's zero-change result is captured as evidence. Standardisation applies to names too, and the naming scheme is part of the architecture rather than cosmetics, because a name that differs between two writers' documents is a defect no amount of testing will find.

**Documentation-first.** The design is written before it is built, and the artefact produced during the build is the *evidence* rather than the document. This ordering matters because documentation written afterwards describes what was built including its accidents, whereas documentation written first makes each accident visible as a deviation. Documentation is not peripheral here: the standard requires it — `Prepare a technical document reflecting the solution in detail for agreement and sign-off` and `The purpose of documenting the completion of the installation or up-grade` (both Domain 6) — while the specific obligation to capture findings, manuals, steps, screen captures, verifications and references is the HDTN topic sheet's requirement. The two must be attributed separately and never merged.

**Testability.** A claim that cannot be tested is not a design element. Every service in the port matrix is reachable by a named command; every trust-boundary row is verifiable by a permitted flow and a denied flow; every redundancy mechanism is verifiable by killing the active component and observing the transition; and every playbook is verifiable by a second run. `Test-ServiceEndpoints.ps1` exists so the port matrix is executable rather than merely tabulated, and the traceability matrix maps every brief technology to a test case identifier.

**Reversibility.** No change may be irreversible without a stated recovery path, because the environment is remote and administrators cannot physically reach a locked-out firewall. Firewall rulesets are applied by a script that arms a rollback timer; a snapshot is taken before every significant change and deleted once verified; the deliberate routing misconfiguration used to demonstrate loop prevention is captured and then reversed; and the disaster-recovery exercise is defined as reversible operations — seizing or transferring a Flexible Single Master Operations role, restoring a deleted organisational unit from the Active Directory Recycle Bin, restoring a file from the backup repository, and failing over the proxy virtual address. The one action deliberately excluded from routine practice is the `krbtgt` reset, documented as a procedure and executed only with supervisor approval.

### 6.2 Solution Overview

The design delivers a virtualised enterprise network for a 160-person Hong Kong financial-technology firm across a headquarters, one branch office, two small offices and a remote workforce, built entirely on host-only virtual networks on one hypervisor host plus a simulated Cisco topology. There is no physical network hardware of any kind.

The headquarters in Sha Tin is the data centre of record and holds every core service. Identity is provided by one Active Directory forest and domain, `vertexpeak.fyp.lab`, with two writable domain controllers on VLAN 30 (`vpnz-dc01` at 10.10.30.11 and `vpnz-dc02` at 10.10.30.12) and a read-only domain controller at Kwun Tong (`vpnz-brdc01`) that keeps branch authentication alive if the wide-area link fails. Those controllers are also the authoritative DNS servers and authoritative time source for the forest, and the same forest hosts the enterprise certificate authority, so every certificate — for domain controllers, the reverse proxy, the IIS tier, the IKEv2 server, the WireGuard endpoint and the ASA identity — is issued, distributed and revoked through one chain of trust. File services with quota and screening policy (`vpnz-fs01`), block storage (`vpnz-san01`), remote-access VPN (`vpnz-rras01`) and the Linux-side remote-access server (`vpnz-lnxra01`) sit alongside them on the same server segment.

The customer-facing SaaS platform is published from a demilitarised zone and never directly from the internal network. An Nginx pair behind a floating virtual address terminates TLS and re-encrypts to the origin tier; the Windows application tier (IIS on `vpnz-dmzweba01/02`) and the content tier (WordPress on `vpnz-dmzwp01/02`) sit behind that proxy with no inbound path from the Internet. The DMZ is a compartment, not a corridor: it may not initiate any connection toward the internal network for any protocol, its hosts may be managed only through a dedicated DMZ jump host, and it may reach the Internet only outbound and only for name resolution and package retrieval.

Everything leaving the internal network passes through one chokepoint: a pair of Ubuntu hosts running a stateful nftables filter and NAT, sharing a floating virtual address and sitting inline between the headquarters core and the ASA. This is where per-zone egress policy is enforced, where outbound traffic is attributed to a source address and logged, and where the failure of a policy change is contained by a rollback timer. Beyond it, the ASA owns the edge: the DMZ boundary, address translation for published services, and a site-to-site IPsec tunnel to Wan Chai.

Routing is dynamic and separated by domain rather than by preference. Headquarters and Kwun Tong run a single OSPF area 0 across their wide-area link, so a link failure causes a real reconvergence event that can be observed and documented. Macau and one inherited transit segment still run EIGRP as autonomous system 100, and their routes enter OSPF at exactly one router through an explicitly numbered, tagged, one-way redistribution point. At the boundary, the headquarters edge router is autonomous system 65001, peering with the simulated primary provider and a secondary peer, and Wan Chai is modelled as a small autonomous system of its own. The access layer is a three-tier design — core, aggregation and access — with two core switches in a redundant pair running RSTP with an explicitly configured root bridge, and gateway redundancy for the server, user and storage segments provided by HSRP on the switch virtual interfaces.

Branch connectivity is deliberately heterogeneous, because a single mechanism could not serve four sites honestly. Kwun Tong reaches headquarters over a routed link and runs the same OSPF process. Wan Chai has two independent paths — an IPsec site-to-site tunnel on the ASA and a WireGuard tunnel on the nftables pair — and its integration segment is the least-privileged segment in the company, holding no production credentials. Macau is the EIGRP spoke. Remote staff connect by two independent mechanisms, certificate-authenticated IKEv2 through RRAS and OpenVPN, with a WireGuard remote-worker pool as a third option. Remote users reach the services their role requires and are categorically forbidden from reaching the management plane.

Operations are automated from a single control node (`vpnz-mon01`) that is also the Git server, the monitoring stack and the configuration archive. Ansible manages the Linux estate over SSH and the Windows estate over WinRM; because the Cisco estate is simulated and exposes no reachable management interface, device configuration is held in version control as text with a documented gap analysis of what a real device would require. PowerShell performs the Windows and directory work, Bash the procedural Linux work, and every run writes a committed log. Above the automation layer sits a strictly read-only agentic layer (`vpnz-ai01`) with four declared tools that triages alerts into evidence-backed narratives and *proposed* changes for human approval, with no write path by construction.

The environment is therefore best understood as three planes. The **data plane** carries user, server and branch traffic subject to the zone matrix. The **management plane** lives on its own address space and is reachable only from `Z-MGMT`. The **automation and observability plane** — control node, Git, monitoring, agent — reads and configures the other two, which is exactly why it is both the most valuable component to operate and the most valuable to compromise.

### 6.3 Physical and Virtual Infrastructure

#### 6.3.1 The hypervisor host

The entire virtual estate runs on one student-owned physical machine, `vpnz-hvhost01`, with a management address of 10.20.20.10 in the management VLAN. There is no lab cluster, no shared storage appliance and no second host, which is the project's single largest availability limitation and is recorded as such rather than glossed over: **the hypervisor host is a single point of failure for all nineteen virtual machines.**

#### 6.3.2 Hypervisor recommendation and alternatives

The recommended default is **VMware Workstation Pro 17.6.2** on a Windows 11 Pro host (24H2 or 25H2, build 26100.x). The release notes page for that build is retained in the references folder as evidence of the version's existence — VMware Workstation 17.6.2 Pro release notes, `https://techdocs.broadcom.com/us/en/vmware-cis/desktop-hypervisors/workstation-pro/17-0/release-notes/vmware-workstation-1762-pro-release-notes.html`. Whether the free-personal-use entitlement still applies to this exact build at build time is an assumption that must be re-checked; if it has changed, the group switches hypervisor rather than paying. The recommendation rests on three properties, in order of importance.

First, the Virtual Network Editor creates an arbitrary number of host-only virtual networks with a chosen subnet *and* with the built-in DHCP service switchable off on each one. This is the hardest requirement to satisfy on the alternatives and it is a hard requirement here: the design needs nine isolated networks with the hypervisor's DHCP disabled on every one, because the Active Directory DHCP service must be the only DHCP authority in the lab, and because a host-only network is the mechanism that stands in for VLAN isolation. Second, the snapshot and clone workflow makes a nineteen-machine build reproducible across four students on four different laptops and lets evidence be regenerated rather than merely retained. Third, it has the broadest documentation and tutorial base, which matters because three of the four group members will use it for the first time.

The following matrix is normative. `PERMIT` means allowed and logged; `DENY` means dropped and, where the device supports it, logged; `REVIEW` means allowed only for the named protocol and only to the named destination, and only while the review case that justified it remains open. Read across for the source zone and down for the destination zone.

| From ↓ / To → | `Z-MGMT` | `Z-SERVER` | `Z-CORE` | `Z-EGRESS` | `Z-DMZ` | `Z-USER` | `Z-STUDENT` | `Z-WAN` / Internet |

| **`Z-STUDENT`** | DENY | DENY | DENY | DENY | DENY | DENY | PERMIT (intra-segment only) | **DENY — no egress at all, by design** |
| **`Z-WAN` / Internet** | DENY | **DENY** | DENY | REVIEW (the four VPN ports only) | REVIEW (HTTPS 443 and HTTP 80 to the published proxy address only; ICMP echo) | DENY | DENY | PERMIT |

Five rows carry the architectural argument and should be called out. `Z-DMZ` → internal is **denied for every protocol**, which is what makes the DMZ a compartment rather than a staging area. Internet → `Z-SERVER` and Internet → `Z-USER` are **denied entirely**, so the only Internet-reachable elements are the published proxy address and the four tunnel ports. `Z-REMOTE` → `Z-MGMT` is **denied entirely**, so a staff laptop with a valid certificate and valid credentials still cannot reach the management plane. `Z-STUDENT` has no egress at all, and the deliberate-misuse tests are sourced from it precisely so the denial is proven rather than asserted. And the AI agent is a source zone in its own right, with a read-only permit list and no destination anywhere that accepts a write from it.

Every permitted flow is logged, and the design requires one captured denial per zone boundary so the *deny* path is evidenced as concretely as the permit path. Any later writer documenting a live test must cite the trust-boundary rule identifier it verifies.

#### 6.5.2 HQ-to-branch routing design

Three branch patterns are configured deliberately, because a single pattern could not demonstrate the range of connectivity the brief requires.

**Kwun Tong — routed, same routing domain.** `VP-BR-EDGE-01` forms an OSPF adjacency with the HQ edge router across the `/30` link, and the branch's four segments are advertised into area 0. Traffic is routed, never bridged: **no VLAN is stretched between HQ and any branch**, which removes a class of failure in which one broadcast domain's problems are shared across a wide-area link. The branch keeps an RODC so Kerberos authentication and local DNS continue if the link fails; this is a deliberate availability decision with a security cost the report must state — a read-only controller at a less protected site holds credentials, so its password-replication policy is documented and restricted rather than left at defaults. Branch DHCP is served from HQ over the link with a local relay; the RODC is a DHCP relay and a third DNS server, and it is **never** the only resolver for any client, because a branch whose only resolver is unreachable is a branch that cannot log in.

**Wan Chai — tunnelled, two independent paths.** Wan Chai deliberately has redundant, heterogeneous connectivity, because it also hosts the least-privileged segment in the company. The ASA provides an IKEv2 site-to-site IPsec tunnel and the nftables pair provides a WireGuard tunnel, independent in protocol, implementation and cryptographic design. Which carries production traffic is an open decision: the WireGuard site-to-site peer may be represented by a dedicated Ubuntu guest emulating the branch encrypting gateway, or the WireGuard role may be reduced to remote workers with the ASA carrying the site-to-site tunnel. Either way, **the design must not claim WireGuard on a Cisco device**, because a Cisco router cannot terminate WireGuard, and the report must record the decision taken. The Wan Chai integration segment (VLAN 131, 10.10.131.0/24) holds no production credentials, and the site's `/24` segments are advertised back to HQ through the tunnel.

**Macau — the domain boundary.** Macau runs EIGRP AS 100 and reaches HQ over a `/30` link that is the boundary between two routing domains. Its routes enter OSPF at exactly one router, `VP-HQ-EDGE-01`, through one-way tagged redistribution. Macau has no local server, no local domain controller and no local DNS, which is an honest and deliberate limitation for a four-person office: its availability depends entirely on the link, and the report must say so rather than implying site resilience that does not exist.

#### 6.5.3 How traffic between sites is controlled

Two mechanisms operate together. The first is routing policy: exits from one domain into another are filtered, and only the redistribution point may translate routes between domains, so a prefix's origin is always determinable. The second is the trust-boundary matrix of §6.4.3, enforced independently of routing: being *routable* to a destination and being *permitted* to reach it are different things, and the design requires both. Inter-site traffic is subject to the same matrix as intra-site traffic — a branch workstation reaching a headquarters server is a `Z-USER` → `Z-SERVER` flow regardless of the path — with the single addition that branch router management addresses are reachable only from `Z-MGMT`. A wide-area link therefore changes the *path* of a flow, never its *verdict*.

### 6.7 Routing Architecture

#### 6.7.1 The OSPF domain

OSPF runs as a single area 0 across headquarters and the Kwun Tong branch, joined by the 10.10.100.32/30 link. A single area is used because multi-area hierarchies add failure modes a 12-week schedule cannot verify honestly, and the assessed value lies in a working, breakable domain rather than hierarchy theory. Authentication is enabled on the core links so a device cannot join the domain without the shared secret. Interfaces that cannot legitimately form an adjacency — access ports, the storage segment, the isolated lab — are configured passive, which suppresses pointless hello traffic and removes an injection surface. The default route is generated at the edge by `default-information originate` at `VP-HQ-EDGE-01`, so interior routers hold a default rather than the provider's table, keeping the interior topology small and the propagation of external instability contained. Loopbacks are advertised so each router has a stable, single-path prefix.

#### 6.7.2 The EIGRP domain

EIGRP autonomous system 100 serves the Macau office and one inherited transit segment, in classic mode at the default administrative distance of 90. The report must state that value and justify it, because the design relies on default administrative distance as part of the loop-prevention argument and a reader cannot evaluate the argument unless the values are stated. EIGRP's regular route preference, composite bandwidth-and-delay metric and proprietary scope are properties the group must be able to explain; the confined scope is a migration decision, not a recommendation.

#### 6.7.3 The eBGP peering

Vertex Peak is autonomous system 65001. `VP-HQ-EDGE-01` peers with the simulated primary provider (AS 65000) over 10.10.100.0/30, with an alternate provider (AS 65002) over 10.10.100.40/30, and Wan Chai is modelled as a small autonomous system, 65021. The session is deliberately simple because Packet Tracer's BGP support is basic: neighbour establishment, explicit `network` statements, an inbound prefix list, an outbound route-map capable of path prepending, `maximum-prefix` as a safety valve, and local preference to select the primary path. Failover is demonstrated by shutting the primary session down and capturing the routing-table change. Route reflectors, confederations, `add-path`, RPKI and BGPsec validation are outside what the simulator models and are never claimed.

#### 6.7.4 The redistribution point, and loop prevention

**There is exactly one redistribution point in this design, and it is `VP-HQ-EDGE-01`.** Everything that crosses between the OSPF domain and the EIGRP domain crosses there and nowhere else. Where the baseline's own narrative also records redistribution activity at `VP-HQ-CORE-01`, this design chapter treats `VP-HQ-EDGE-01` as the single normative redistribution point and notes the inconsistency explicitly rather than reproducing it silently, because a design with two redistribution points between the same two domains is precisely the design that loops.

Loop prevention rests on four measures, each addressing a specific mechanism by which redistribution creates a loop.

**Route tags.** Routes redistributed from EIGRP into OSPF are tagged 100 and routes from OSPF into EIGRP are tagged 200, and every redistribution statement denies routes bearing the tag of the domain they are entering. This is the primary defence: a route that has crossed the boundary once cannot cross back, because the tag travels with it and the receiving domain refuses to re-advertise it.

**Prefix lists.** Explicit prefix lists enumerate the prefixes that may be redistributed in each direction. The tag prevents a round trip; the prefix list prevents an unintended advertisement in the first place and prevents an aggregate or a transit link leaking into another domain. The lists are kept narrow — the branch's own segments, the HQ server and user segments, the loopbacks — with everything else denied by the implicit deny at the end of the list, which must be stated rather than assumed.

**One-way, per-prefix-set redistribution.** Redistribution is configured once per direction with a distinct prefix set each way. No statement redistributes everything, and no statement uses the same filter in both directions, because that is where a route can return by a different path than it left by.

**Administrative distance.** The design relies on default administrative distance — EIGRP internal at 90, OSPF at 110 — as a conscious, stated choice. Its consequence is that when the same prefix is learned from both domains, the EIGRP-learned route wins for EIGRP-originated prefixes. The reason for keeping defaults rather than tuning them is auditability: a reader can verify the design against published defaults, whereas a tuned distance is a project-specific fact invisible in the configuration and plausible-looking in a failure.

The design also exercises the failure: a deliberate mutual, un-tagged redistribution is configured once, the resulting loop captured in the forwarding table and a traceroute, and the configuration then repaired. A loop produced, observed and fixed is stronger evidence than an assertion that tags prevent loops, and the exercise doubles as a Domain 6 troubleshooting case.

### 6.8 High Availability Design

High availability operates at three levels, and separating them is essential because their strengths differ. *Gateway* redundancy keeps a subnet reachable when one Layer-3 device fails; *service* redundancy keeps an application answering when one server fails; *path* redundancy keeps traffic flowing when a link fails. Only the first two are demonstrated as services: path redundancy exists in the simulated topology, but genuine physical path redundancy cannot exist on a single hypervisor host, and that limitation is stated rather than implied.

#### 6.8.1 HSRP on switch virtual interfaces

Hot Standby Router Protocol provides gateway redundancy in the headquarters access layer, where the gateway is a switch virtual interface. It is used rather than VRRP at this layer for a specific and honest reason: **HSRP is what the simulator implements reliably**, and a design specifying something the tool cannot model produces unverifiable claims. Four groups run, one per switch virtual interface — group 1 on VLAN 30, group 2 on VLAN 40, group 3 on VLAN 70 and group 4 on VLAN 80 — with `VP-HQ-CORE-01` active at priority 150 with preemption enabled and `VP-HQ-CORE-02` standby at priority 100. A single group cannot serve four SVIs, because one virtual MAC cannot answer for four subnets. The virtual MAC addresses are `0000.0c07.ac01`, `0000.0c07.ac02`, `0000.0c07.ac03` and `0000.0c07.ac04`, from the HSRPv1 formula `0000.0c07.acXX` with XX the group number in hex.

| Segment | Subnet | Virtual gateway (HSRP) | Active / standby |
|---|---|---|---|
| VLAN 30 `SRV-HQ-1` | 10.10.30.0/24 | 10.10.30.254 | `VP-HQ-CORE-01` / `VP-HQ-CORE-02` |
| VLAN 40 `USER-HQ-STF` | 10.10.40.0/23 | 10.10.40.254 | `VP-HQ-CORE-01` / `VP-HQ-CORE-02` |
| VLAN 70 `STUDENT-LAB` | 10.70.0.0/24 | 10.70.0.254 | `VP-HQ-CORE-01` / `VP-HQ-CORE-02` |
| VLAN 80 `STORAGE-HQ` | 10.10.80.0/24 | 10.10.80.254 | `VP-HQ-CORE-01` / `VP-HQ-CORE-02` |

The physical interface addresses (10.10.30.1, 10.10.40.1 and so on) exist on the switch virtual interfaces and are *not* the client gateway. This is a design rule rather than a preference: if a client is configured with a physical interface address instead of the virtual address, gateway redundancy silently does nothing and the failure stays invisible until the active switch is lost. Failover is priority-based election with preemption — the active router advertises at a fixed hello interval, the standby promotes itself once the hold time expires without a hello, and preemption ensures the intended primary reclaims the active role rather than leaving the topology in a random post-failure state. Detection is therefore timer-based, with a hello interval of the order of a few seconds and a hold time approximately three times that; the exact configured values must be captured from the running device rather than quoted from memory, and the failover is evidenced by `show standby brief` before and after an interface shutdown plus a continuous ping showing no loss beyond the transition.

#### 6.8.2 Keepalived VRRP instances

Where the gateway is a Linux virtual machine rather than a switch, Keepalived provides the same function with a different protocol implementation, and the design contains **two** such pairs. Each is defined by a `vrrp_instance` block in `/etc/keepalived/keepalived.conf` carrying `state`, `priority`, `virtual_router_id`, `virtual_ipaddress`, `preempt` and a `track_script`.

| Instance | Hosts | Subnet | `virtual_router_id` | Virtual address | Priority |
|---|---|---|---|---|---|
| nftables egress pair | `vpnz-nft01` / `vpnz-nft02` | 10.10.50.0/28 | **51** | 10.10.50.10 | 150 master / 100 backup |
| Nginx proxy pair | `vpnz-dmzrev01` / `vpnz-dmzrev02` | 10.10.90.0/24 | **61** | 10.10.90.10 | 150 master / 100 backup |

Three details carry the architectural argument. First, **the two virtual router identifiers differ** (51 and 61), because reusing one identifier on two segments that could ever be joined would produce two masters and a duplicate-address condition — a failure that is easy to create accidentally and hard to diagnose. Second, preemption is enabled in both instances so the intended primary always reclaims the role. Third, and most importantly, the `track_script` health checks test the *service*, not the interface: the Nginx pair curls a local health endpoint and the nftables pair verifies that the ruleset is non-empty. A VRRP instance that tracks only its own network interface will happily retain the virtual address while the service behind it is dead, which converts a redundancy mechanism into an outage amplifier. The Nginx instance also owns the published TLS material through `/etc/nginx/ssl/`, and because the virtual address moves with the instance, the certificate must be valid for the virtual *name* rather than for either hostname — which is why the internal PKI issues a certificate covering the service name and both members.

Failover is the VRRP mechanism: the master advertises at a fixed interval; a backup that misses advertisements beyond the master-down interval promotes itself and gratuitously claims the virtual address; gratuitous ARP updates neighbour mappings so traffic follows the address within a broadcast domain. Detection is therefore two-dimensional — an advertisement timeout *or* a failing track script can trigger a transition — which is the advantage a health-check-driven mechanism has over any routing- or DNS-based scheme. The evidence required for each pair is a captured transition: the master is stopped, the virtual address is observed to move, the service is observed to continue answering, and the `keepalived` journal is retained. Both pairs move within a single broadcast domain, so no VRRP-over-tunnel caveat applies. One simplification must be stated plainly: the instances use `auth_type PASS`, which is acceptable within a host-only lab segment and **must be described as a lab simplification, not as best practice**.

#### 6.8.3 What is not claimed

Three claims are deliberately withheld. There is **no** ASA failover pair, because Packet Tracer does not model state replication between appliances, so the perimeter is a single logical device and that is an availability limitation of the design. There is **no** hardware-level high availability — no link aggregation across physical chassis, no dual power supply, no dual-site storage replication — because no physical hardware exists. And the hypervisor host itself is a single point of failure for everything, which is the environment's largest availability exposure and belongs in the risk chapter, not in a footnote.

### 6.9 Security Architecture

#### 6.9.1 The firewall tiers

There are two enforcement layers in series on the path from the internal network to the Internet, and they are deliberately different implementations.

The **first tier** is the nftables pair (`vpnz-nft01`, `vpnz-nft02`) sitting inline on VLAN 50 between the HQ core and the ASA inside interface. It is the egress chokepoint: stateful forwarding with a default-drop policy, NAT (masquerade) on the wide-area-facing interface, named sets for the trust-zone peer groups so policy is expressed against groups rather than long address lists, connection limiting, and a logging prefix on every drop rule so a denial produces an artefact. Its ruleset is a single atomic artefact — `table inet fyp_filter` in `/etc/nftables.conf` with included fragments — which is what makes the change reviewable and reversible; applying it through a script that arms a rollback timer is what prevents the classic remote-firewall lockout.

The **second tier** is the ASA (`VP-HQ-FW-01`), which owns the trust boundary the pair does not: the DMZ. It applies security levels of outside 0, dmz 50 and inside 100; object groups for the server, DMZ, management, user, remote-access and lab networks; dynamic PAT for inside-to-outside traffic and static NAT for published DMZ services; application inspection for protocols that carry addresses inside their payload; and syslog at informational level to the monitoring host. It also terminates the site-to-site IPsec tunnel to Wan Chai. Declared limits: Packet Tracer's ASA is a reduced legacy-ASA model, so FirePOWER/SFR, clustering, failover pairs, `shun` and much low-level drop instrumentation are absent and **must never be claimed**.

The division of labour is intentional. The pair sees *everything leaving the enterprise* and is where per-zone egress policy, attribution and logging live; the ASA sees *everything crossing the DMZ and the Internet edge* and is where publication, translation and the site-to-site tunnel live. A packet from a workstation to a web server passes both, and a rule mistake in one language is unlikely to be reproduced in the other. This two-layer position is the concrete implementation of the defence-in-depth principle, and it is why the pair is drawn inline rather than beside the ASA.

#### 6.9.2 DMZ design

The DMZ's defining rule is that it may not initiate anything toward the internal network, for any protocol. Every other decision follows.

Inbound, only the published addresses are reachable and each maps to exactly one service: the proxy address to the Nginx virtual address, the application address to the Windows tier, the content address to the WordPress node, and the tunnel address reserved for the remote-access ports. No DMZ host is reachable directly from the Internet for any other port, and nothing in the DMZ is reachable at all except on the published path. The proxy terminates TLS and re-encrypts to its upstreams, so traffic inside the DMZ is encrypted even though the DMZ is not trusted; HSTS is enabled; the minimum protocol version is TLS 1.2 with 1.3 preferred; and the cipher-suite negotiation is captured with `openssl s_client` as evidence rather than asserted.

Outbound, only the proxy and the Windows application nodes may reach the Internet, only to port 443, only outbound-initiated, and only for name resolution and package retrieval; the content tier is not granted this. The asymmetry is worth stating: an outbound path from a compromised web host is the standard exfiltration route, and limiting it to two named hosts with one permitted port is a control testable by attempting the same connection from a host that should not have it.

Management of the DMZ is possible only through `vpnz-dmzjump01` (10.10.90.27), itself reachable only from the management zone. There is no direct administrative path from a workstation to a DMZ host, and no DMZ host accepts administrative logins from anywhere else, which makes the jump host a deliberate bottleneck whose logs show every administrative action taken inside the DMZ.

One open decision is recorded rather than assumed: whether DMZ hosts are domain-joined or isolated in a workgroup. Domain-joining simplifies administration and certificate distribution but means a compromised DMZ host caches domain credentials; isolating them removes that exposure at the cost of a second account and certificate management path. The decision and its justification must be recorded either way, and a dedicated Group Policy object exists for the DMZ servers regardless, so a minimum baseline — no domain administrator logon, restricted logon rights, separate local accounts — applies in both cases.

#### 6.9.3 Certificate-based authentication and the internal PKI

One certificate chain serves the whole environment, and that is the point: a certificate issued to a Linux host is trusted on Windows and vice versa, so no component has to trust anything issued outside the chain. `VP-ROOT-CA` is an offline root and `VP-ISSUING-CA-01` the online issuing authority.

| OpenVPN server and clients | `CN=server-vpnz-lnxra01`, `CN=client-{staffid}` | Issued by Easy-RSA on the Linux side; OpenVPN uses the common name as its identity |

If the group concludes during the build that a two-tier PKI is more operation than four people can run in twelve weeks, the documented fallback is a single tier with `vpnz-dc01` issuing directly, and the report must state which model was used rather than describing the intended one. Validity periods are a design parameter, not a default: the root authority is twenty years, the issuing authority ten, and any internal TLS certificate a maximum of 397 days with ninety preferred, renewed by a documented dry run. No self-signed certificate appears in the delivered design except during a documented build step where it is later replaced. Public-name certificates come from the internal PKI, so the lab must show and explain a name-mismatch warning; that warning is expected behaviour here and must be presented as such, because **no real public certificate authority is used and none is claimed**.

Two properties deserve statement as security properties rather than configuration. Revocation is exercised: the design regenerates a certificate revocation list and demonstrates that a revoked OpenVPN client fails to connect, because a revocation mechanism never exercised is not a control. And private-key handling on the Linux side is explicit: the Easy-RSA PKI directory has mode 0700, holds private keys, and is on the list of paths that may never be committed to version control.

#### 6.9.4 Management-plane protection

The management plane is the most restricted zone and is protected by four independent measures. It is **addressed separately**, in `10.20.0.0/16` and VLAN 20, so exposing it requires a deliberate routing act rather than an accident. It is **reachable only from itself**: management protocols — SSH, RDP, WinRM, the Windows Admin Center gateway, SNMPv3 and syslog — are permitted from `Z-MGMT` to every zone, and from every zone back to `Z-MGMT` only for syslog and SNMPv3. It is **closed to remote users**: `Z-REMOTE` to `Z-MGMT` is denied outright, so a valid certificate and valid credentials on a staff laptop still confer no administrative reach. And it **does not trust in-band convenience**: sessions use SSH and RDP with named personal accounts, `PermitRootLogin no` and password authentication disabled on Linux, and SNMPv2c with community strings is forbidden everywhere in favour of SNMPv3 in authenticated-and-privileged mode.

Two further controls close the most common management-plane failures. The isolated lab segment cannot reach the management plane at all, and neither can the branch infrastructure — `Z-WAN` to `Z-MGMT` is denied, so a branch router cannot be used as a pivot into headquarters management. And the automated administrative path is credential-scoped: the agent's read-only account and the automation service account hold the minimum grants their function requires, so a compromise of the automation path does not yield Domain Admin.

#### 6.9.5 Logging and monitoring pipeline

Every layer produces logs and every log has a destination. Linux hosts forward to the monitoring host on UDP 514 through a dedicated `rsyslog` configuration; the ASA sends syslog at informational level to the same host; the Cisco devices do the same from within the simulated topology; and Windows hosts retain event logs locally for read-only consumption by the agent, with the advanced audit subcategory set — logon, logon failure, account lockout, account creation, group membership change, service installation — enabled by a dedicated policy object. The nftables pair logs every denial with a prefix, which converts the trust-boundary matrix from a document into a stream of events. The pipeline terminates in the monitoring stack on `vpnz-mon01`, where logs are stored, indexed and made searchable, and where the alert rules that feed the triage workflow live as version-controlled files rather than dashboard settings.

Log storage is a design concern rather than a by-product. The monitoring host retains logs and metrics for a bounded period, and the boundary is stated: this retention is sufficient for project verification and demonstration and is **not** a compliance-grade archive, because the design is aligned with selected controls and is not certified against any framework.

### 6.10 Storage Architecture

#### 6.10.1 iSCSI target and initiator design

The storage tier demonstrates block storage independent of any single host's local disks along with a least-privilege storage access model. The target is `vpnz-san01` on the storage segment — VLAN 80, `STORAGE-HQ` 10.10.80.0/24 at 10.10.80.21 — running the Windows Server iSCSI Target Server role. Three targets are published, of 20 GB, 40 GB and 60 GB. Their target IQNs are **derived by Microsoft's iSCSI Target Server from the server's own IQN plus the target name and cannot be set**, so they read `iqn.1991-05.com.microsoft:vpnz-san01-storage-lun01.target`, `…-lun02.target` and `…-lun03.target`, captured with `Get-IscsiServerTarget`. The canonical project string `iqn.2026-01.lab.fyp.vertexpeak:storage-lun0N` therefore names the **initiator** endpoint — the initiator on `vpnz-dmzweba01` — not the target (Rev 1.1 ruling C-06). The first carries the web-tier data, the second is the backup staging volume Windows Server Backup writes to, and the third is thin-provisioned and deliberately left unused, so the design demonstrates creating a LUN without pretending it is in production use.

Three properties matter more than the LUN sizes. **Network isolation**: the storage segment has no routing beyond the core, so an iSCSI session cannot originate from a workstation, a branch or the DMZ — storage traffic is not merely filtered but unroutable from anywhere that should not use it. **Initiator identity**: access control is enforced at the target by an initiator allow-list of qualified names and a CHAP secret per initiator, with mutual CHAP added if time permits; this binds access to a *host identity announcement* rather than a user account and is therefore not transferable by stealing a user's credentials alone. And the **honest boundary**: a single path with no MPIO, and no claim of Windows failover clustering, Scale-Out File Server or Storage Spaces Direct, because one hypervisor host cannot provide a genuinely independent second storage path and a clustered claim would be unverifiable.

#### 6.10.2 File service design

File services are provided by `vpnz-fs01` on VLAN 30 at 10.10.30.21, serving four managed shares under `D:\Shares\` — `Finance` (quota 20 GB), `Engineering` (10 GB), `SalesRO` (10 GB) and `Public` (5 GB) — with the file screen `*.exe;*.vbs;*.mp3` applied and a storage-report schedule producing usage evidence. Access is by SMB 3.1.1, and the permission model is two-layer as everywhere: share permissions and NTFS permissions set the access boundary, and domain-local groups mapped one-to-one onto the shares (`DL-{Share}-{RW|RO}`, populated from `GG-Finance-RW`, `GG-Finance-RO`, `GG-Engineering-RW` and `GG-Sales-RO`) carry the grants. Drive letters are delivered by policy with item-level targeting, so a finance user sees `F:` and an engineering user sees `G:`, and the mapping is a property of group membership rather than a manual step.

The operational limits are recorded as design facts rather than omissions. A local cached copy of required material is configured for the branch, but this is a **configuration and evidence** arrangement, not a demonstration of site-level data replication. The backup path is Windows Server Backup to the second LUN plus a documented off-host copy of configuration and evidence through the Linux-side backup job; the design states plainly that this is not a full virtual-machine or hypervisor-level backup, because no such licence exists here and claiming one would be a false claim about capability. Snapshots are used during change, never as backup. And the file tier stores no real customer data: the scenario's 260 brokerage clients and 14,000 end-user seats are narrative context, and the project's non-goals prohibit real customer data outright.

### 6.11 Identity and Access Architecture

The identity design is one forest, one domain and one tree — `vertexpeak.fyp.lab`, NetBIOS `VERTEXPEAK`, Kerberos realm `VERTEXPEAK.FYP.LAB`, functional level Windows Server 2025, a single user principal name suffix. Two writable domain controllers serve headquarters and one read-only domain controller serves Kwun Tong. All five Flexible Single Master Operations roles are held by `vpnz-dc01` initially, and transferring the PDC emulator role to `vpnz-dc02` is a documented disaster-recovery exercise rather than a routine task.

The organisational structure is a single `OU=VertexPeak` tree separating by function and site: users beneath `OU=Users` and then by site and department; computers beneath `OU=Computers` into `OU=MemberServers`, `OU=Tier0-DomainControllers`, `OU=DMZ-Servers`, `OU=Workstations` and `OU=LinuxServers`; groups beneath `OU=Groups`; service accounts beneath `OU=ServiceAccounts`; administrators beneath `OU=Admins` divided into `OU=Tier0`, `OU=Tier1` and `OU=BreakGlass`; documentation objects beneath `OU=Network`; and `OU=Quarantine` with `OU=Disabled` and `OU=NewObjects` for objects awaiting disposition. The default `CN=Users` and `CN=Computers` containers are used by the read-only controller and by nothing else, and every user and computer object must live in the tree before the build is considered complete — itself a testable condition.

Authority is delegated rather than granted wholesale. The helpdesk group receives password reset and account-control write permission on `OU=Users` only. Server administrators receive local administrative rights on member servers through Group Policy restricted groups or a managed local-administrator password solution, **not** through Domain Admins. Only the two Tier-0 administrators may authenticate to the domain controllers or the certificate authority. And site awareness is configured so each subnet in the addressing plan maps to exactly one Active Directory site (`HQ-ShaTin`, `BR-KwunTong`, `WC-WanChai`, `MO-Macau`) with no subnet unmapped, because an unmapped subnet means a client authenticates against a controller it should not have chosen.

**How the Linux estate consumes identity.** The design requires the same four named administrators to authenticate on both platforms with an identical outcome whether or not the Linux hosts are domain-joined, and it accepts either implementation. In the local model, `gg-infra-admins` is a local group whose membership mirrors `GG-Infra-Admins`, with the four personal accounts created locally under the same names. In the joined model, `realmd` and `sssd` join the hosts to `vertexpeak.fyp.lab` and the local group becomes a mapped group resolving to the same membership. In both cases administrators log in with personal account names and never as `root`; SSH keys are Ed25519, one per administrator, with public keys held in the Ansible repository and private keys never stored on the control node; and `PermitRootLogin no` is mandatory everywhere. On the Windows side the same administrators have domain accounts, and personal accounts are kept separate from service accounts, which exist only for automation and are members of no privileged group except the single group their function requires.

Exactly one identity path crosses into the DMZ, and it is deliberately narrow. The content tier binds to the directory with `svc_ldapbind`, a member of `GG-DMZ-LDAP-Readers` and nothing else, using LDAPS on port 636. The directories are reachable from the DMZ only for LDAP and LDAPS and only for that account. This is the design's most sensitive cross-boundary dependency, because it is the one place where an untrusted zone reads a trusted one, so it is bounded to a single account, a single protocol pair and a single read operation.

One identity risk is inherent and is stated rather than mitigated away: the headquarters domain controllers and the certificate authority are Tier-0 assets, and the authority is the fundamental one, because compromising the issuing authority allows an attacker to mint a credential every component will trust. That is why the root authority is offline and why Tier-0 authority is confined to two named people.

### 6.12 Automation Architecture

#### 6.12.1 The control node

There is exactly one automation control node: `vpnz-mon01` on VLAN 30 at 10.10.30.31, running Ubuntu Server 24.04.3 LTS. It runs the Ansible control node, the Git server, the monitoring and logging stack, the network-device configuration archive and the Linux-side time source. No playbook is ever executed from a student laptop, for an evidentiary reason rather than a stylistic one: a run executed from an unpinned laptop produces a log that cannot be reproduced, and the project's central automation claim is reproducibility.

| Component | Version | Role |
|---|---|---|
| `ansible-core` | 2.18.x with the community package 11.x | Configuration management for both Linux and Windows targets |
| `pywinrm` | 0.5.0 | WinRM transport for Windows targets |
| PowerShell (on the Windows targets) | Windows PowerShell 5.1 in-box; PowerShell 7.4 LTS on `vpnz-jump01` for authoring | The native Windows management surface the playbooks and scripts drive |
| Git | 2.43 or later | Version control, with bare repositories or a lightweight web front end over SSH |

#### 6.12.2 The inventory model

The inventory is a single file, `inventory/lab.ini`, with six groups — `linux_servers`, `windows_servers`, `dmz`, `network_devices`, `ai`, `mgmt` — and group variables in `group_vars/`: `all.yml` for values common to everything (domain name, time servers, resolvers, administrative groups), `windows_servers.yml`, `linux_servers.yml` and `dmz.yml`. The group structure is a security model as well as an organisational one, because `dmz` is a separate group precisely so that no playbook can apply a server baseline to a DMZ host by accident, and a task that must run only in the DMZ has to name that group explicitly.

Three properties of this model matter. Values are declared once: the domain name, resolver pair and time source appear in `all.yml` and nowhere else, so a change of resolver is a one-line change with a reviewable diff. Hosts are grouped by *role* rather than by name, so adding a second proxy is an inventory edit rather than a playbook edit. And the `network_devices` group is declared even though it cannot be reached, because declaring it makes the gap visible in the configuration instead of hiding it in prose: the group exists, its members are recorded, and the playbook that would configure them is written and tested against the configuration files rather than against the devices.

#### 6.12.3 The playbook structure

Nine playbooks, seven roles and a set of Jinja2 templates make up the automation surface under `C:\FYP\04-automation\ansible\`.

| Playbook | Purpose | Targets |
|---|---|---|
| `01-baseline-windows.yml` | Base configuration of Windows guests: name, addressing, WinRM with an internal-CA certificate, time, audit policy | `windows_servers` |
| `02-baseline-linux.yml` | Base configuration of Linux guests: addressing, time, hardening, `rsyslog` forwarding, exporters | `linux_servers` |
| `03-nginx-reverseproxy.yml` | Nginx configuration, upstream pools, TLS material placement, virtual hosts | `dmz` |
| `04-keepalived.yml` | VRRP instances, priorities, virtual addresses and health-check scripts | `dmz`, and the egress pair |
| `05-nftables-egress.yml` | The atomic ruleset, sets, NAT, connection limits and logging, applied with the rollback guard | the egress pair |
| `06-wireguard.yml` | Interface configuration, peer addressing and allowed prefixes | the egress pair, and the branch peer |
| `07-ad-users.yml` | User, group and organisational-unit provisioning in the directory | the domain controllers, via a Tier-1-scoped path |

Roles are `common`, `nginx`, `keepalived`, `nftables`, `wireguard`, `winrm` and `ad_users`. Templates are Jinja2 — `nftables.conf.j2`, `keepalived.conf.j2`, `wg0.conf.j2` — so a configuration difference between two hosts is expressed as a variable rather than a divergent file. Every playbook supports check mode, and the design requires a check-mode run before an apply and a second real run after it, with the second run's zero-change result captured as evidence of idempotence.

The **gap analysis** is written into the design rather than left to the reader. Ansible cannot reach a Packet Tracer device, because the simulator exposes no reachable SSH server and no API. Network-device automation therefore runs on two tracks. Track A treats `03-build/packet-tracer/configs/*.txt` — the exact intended device configurations — as the source of truth, applies them through the simulator's own interface, and documents the automation step a real device would require. Track B writes and tests the collection and backup mechanisms against the Linux and Windows estate and against the device configurations as version-controlled files. The report must state in plain terms that **no playbook ever logged in to a Packet Tracer device**, and must name the real-equipment alternative — an SSH-based network automation library such as Netmiko or NAPALM — as the step that would close the gap on physical hardware.

#### 6.12.4 Credential handling

Credentials never appear in a playbook, a variable file or a log. Windows automation authenticates as `svc_ansible`, a member of `GG-WINRM-Admins` and nothing else, over WinRM with HTTPS on port 5986 using a certificate signed by the internal authority, with a password rotated by the automation rather than exempt from expiry. Linux automation authenticates with Ed25519 keys whose public halves live in the repository under `files/ssh/authorized_keys/` and whose private halves are never stored on the control node. Any stored secret lives in an Ansible Vault with a single vault password held by the group and not committed. WireGuard private keys are generated per peer, never committed, and their configuration files are both mode 0600 and listed in `.gitignore` alongside `*.key`, `*.pem`, `*.pfx` and the Easy-RSA `pki/` directory.

The controls are verified rather than assumed. A repository-wide credential sweep runs before each tagged release with its output retained, and it includes a deliberate test in which a fake key is committed and the sweep is required to catch it, because an alarm that has never sounded is not a working alarm. Service accounts are documented with a rotated random password held in the group's password manager, have password expiry enabled and self-service change disabled, and appear in the report by name and group membership so the least-privilege claim can be audited rather than believed.

#### 6.12.5 The Git workflow

All automation, configuration templates, device configuration text and verification records live in Git repositories on the control node, mirrored to a second medium so that no single member is the sole holder of any artefact. The workflow is branch-per-task: a change is made on a branch, reviewed by a second member, merged, and released by tag (`v0.1` through `v1.0`). The review is recorded in the meeting minutes as well as in the commit history, because the client's due-diligence item asks for a *process* of reviewed change, not merely a tool that could support one. Every run writes a timestamped log into `04-automation/runs/`, and those logs are committed so the verification chapter can cite them by filename.

One boundary must be stated because the standard mentions the concept and it would be easy to over-claim. `Continuous integration and continuous delivery\deployment pipelines concepts` is a **know/understand** line in Domain 5. This project documents the concept and operates a Git review-and-tag workflow, but it **builds no pipeline** — no build server, no automated test gate and no artefact promotion — and the report must say exactly that rather than listing CI/CD among the delivered features.

### 6.13 AI Operations Architecture

The agentic layer is placed on one host, `vpnz-ai01`, on VLAN 30 at 10.10.30.51 in the trusted server zone, and its architecture is defined primarily by what it is *not* permitted to do.

**What it is allowed to read.** Four tools and no fifth. `get_active_alerts` reads the current alert set from the Alertmanager API over HTTPS. `get_interface_stats` reads interface counters and error rates by polling the Packet Tracer device estate over SNMPv3 and by reading interface statistics on Linux hosts. `get_auth_failures` reads failed-login events — Windows Security event 4625 and `sshd` failures from the journal over SSH. `draft_change_proposal` reads nothing external; it composes text and writes it to a local proposals directory. The tool definitions are declared as manifests under the agent runtime's skills directory, written in a form that would be expressible as Model Context Protocol tool definitions so the surface does not depend on a particular runtime.

**What it is allowed to change.** **Nothing.** There is no write path. The agent cannot modify a device, service, rule, certificate or directory object, because no tool exposes such an operation and the single credential it holds does not permit one. Its only side effect in the environment is creating a text file under a proposals directory on its own host. Excluding autonomous remediation is a deliberate, stated design decision with a specific justification: unsupervised change would make the project's own verification results irreproducible, because the state under test would change between test and re-test, and it would make an unverified language model a component of the security boundary.

**The guardrails.** Seven, each traceable to a named risk.

| Guardrail | Implementation | Risk addressed |
|---|---|---|
| Read-only credential | `svc_aiagent`, a member of `GG-AI-ReadOnly` only; never a member of Domain Admins | Blast radius and privilege escalation |
| No stored device credentials other than that account | Enforced on `vpnz-ai01`; no credential file for any device exists on the host beyond that one account | Credential theft and lateral movement |
| A closed tool surface | Four declared tools; adding a fifth is a reviewed design change recorded in the decision log | Unbounded capability growth |
| Full invocation audit | Every invocation appended to `/opt/openclaw/logs/agent.jsonl` with a prompt hash and the tool calls made | Auditability and after-the-fact reconstruction |
| Rate limiting on tool calls | A hard ceiling per invocation and per hour | Cost, and a runaway loop becoming a denial of service against the monitoring API |
| Network placement restricted to the management and monitoring ports | Permitted destinations are the read-only poll ports only, with no path to the user, DMZ or lab zones | Lateral movement |
| Mandatory human approval | Every output is labelled "proposed — requires human approval" and the workflow terminates at a person | Unreviewed action and hallucination reaching production |

**The workflow.** An alert from the monitoring stack arrives as a webhook, or a schedule fires. The agent calls at most the four declared tools within its budget and produces two artefacts: a triage note citing the tool result behind each claim and stating what it could not determine, and a proposed change in diff form as text. A human reads both, decides, and executes or discards. Nothing further happens without that decision.

**The honesty obligations that attach to this layer.** Four must be stated in the chapter and reflected in the evidence. The first is coverage: the WSOS 2026 contains no AI content at all, so this layer is innovation beyond the standard and cannot be justified by citation. The second is uncertainty about the runtime itself: its version, installation method, skill format and default ports could not be confirmed at design time, which is why a timeboxed feasibility spike must produce an explicit decision by week 6 and why no version, licence or capability claim may be published without a screenshot of the running instance and a citation to the documentation actually used. The third is failure: hallucination and false positives must be documented honestly, with the prompt that produced them, because a documented failure is a stronger academic result than a hidden one. The fourth is evaluation: the chapter must state where the agent helped, where it wasted time, and where a human was strictly required.

### 6.14 Monitoring Architecture

#### 6.14.1 The stack

Monitoring runs on the same control node, `vpnz-mon01`, and consists of four components with distinct jobs. **Prometheus** scrapes metrics from exporters and stores them as a time series. **Grafana** renders provisioned dashboards — `fyp-overview`, `fyp-security` and `fyp-availability` — from files held in Git, so a dashboard is a reviewable artefact rather than a set of settings someone clicked. **Loki** receives and indexes the logs that `rsyslog` forwards. **Alertmanager** evaluates the alert rules, also held as version-controlled files, and is the webhook source that triggers the agentic triage workflow.

#### 6.14.2 Metrics, exporters and collection

| Target class | Mechanism | Port | What is collected |
|---|---|---|---|
| Linux guests (all 10) | `node_exporter` 1.8.x | 9100/tcp | CPU, memory, disk, file system, network interface counters and errors |
| Windows guests (all 9) | `windows_exporter` 0.29.x | 9182/tcp | CPU, memory, volume, service state, network counters |
| Nginx (proxy pair and content nodes) | Local status exporter reading `stub_status` | 9113/tcp (baseline value, confirmed by Rev 1.1 ruling C-08) | Connections, requests, upstream health |
| Cisco device estate (Packet Tracer) | SNMPv3 polling in authenticated-and-privileged mode | 161/udp, traps 162/udp | Interface status, counters, error rates, device availability |
| ASA `VP-HQ-FW-01` | SNMPv3 plus syslog at informational level | 161/udp, 514/udp | Interface and session state; policy denials |
| All Linux guests and all Cisco devices | `rsyslog` forwarding to the monitoring host | 514/udp | System, authentication, firewall and service logs |
| The nftables pair | Native `log prefix "NFT-DROP: "` on every drop rule, forwarded by `rsyslog` | 514/udp | Every denied flow with its source, destination and port |
| Windows guests | Local event logs, exposed read-only to the agent through the least-privileged account | — | Security events used by the triage workflow |

SNMPv2c and community strings are forbidden everywhere in this design, which is why the monitoring account is a named, grouped account rather than a shared string. Discovery and traffic analysis use the tools both the brief and the standard point at: the Cisco discovery protocol for neighbour topology, syslog for events, SNMP for counters, and packet capture on Linux for the manual inspection cases no counter can answer.

#### 6.14.3 Alerting

Alert rules are declared in files, and at least three alerts must be demonstrated firing *and* resolving, because an alert seen only in the firing state has not been shown to clear. The alert set is deliberately small and each rule corresponds to a fault the project can actually inject: an exporter target that stops being reachable, a virtual-address failover and its associated transition, an interface error rate crossing a threshold, a file-system or quota threshold being approached, and a burst of authentication failures. Each alert carries enough labels to be actionable and enough context to be triaged, because a notification saying only "something is wrong" is the failure mode the agentic layer exists to correct.

#### 6.14.4 What "healthy" looks like

A definition of healthy is part of the architecture, because without one the environment can only be described, not verified.

| Area | Healthy condition |
|---|---|
| Metrics collection | Every Prometheus target reports up; no exporter has been absent for longer than one scrape interval |
| Identity | Both writable domain controllers replicate within the site-link interval with no failure outstanding; SYSVOL and share state consistent; time skew below the Kerberos tolerance on every host |
| Name resolution | Every client resolves the domain, the domain controllers and the published names; no client has only one configured resolver |
| Gateway redundancy | One HSRP active router and one standby on every redundant segment; one VRRP master and one backup in each Keepalived pair, with the intended host holding the master role |
| Service availability | Every service in the port matrix answers on its expected port from its expected source zone; every virtual address answers while its owners are individually stopped |
| File and storage | Every managed share is mounted and reachable by its authorised group and by no other; no quota above its warning threshold; the iSCSI session established and the volume online |
| Routing | Every expected adjacency up in the interior domains; a default route present at the edge; the external peer sessions established with the accepted prefix count within the configured maximum |
| Security | The nftables ruleset matches the version in Git with no unauthorised change outstanding; every zone boundary has produced its expected denial events; no credential or key present in the repository; certificate auto-enrolment and renewal report success with no certificate inside its renewal window |
| Automation | Every playbook's most recent run completed with zero failures and, on the second run, zero changes; outstanding failures total zero |
| Agentic layer | The runtime is reachable and the tool surface responds; every invocation present in the audit log; no proposed change sits unapproved and unread |

**Reading the table.** Five patterns are visible, and each has a consequence. First, the best-supported elements are the interior and exterior routing protocols, the directory, the web servers and the automation tooling, all of which the standard names verbatim. Second, a substantial group — FSRM, iSCSI, RRAS, IKEv2, Keepalived, nftables, WireGuard, RSTP and the ASA — rests on either the topic sheet's own wording or a bridge to a generic requirement line, and every one of those entries must carry the word "bridge" or "not named" in the report rather than being presented as coverage. Third, one line of the brief, AI network management, has no WSOS domain at all and is therefore traceable only to this project's own objectives; that is a statement about the standard, not a weakness in the design, but it must be made openly. Fourth, several elements serve the standard's organisational and professional domains rather than its technical ones: the resource budget, the ownership model and the documentation discipline are Domain 1 competences, and the documentation deliverable itself is required by Domain 6. Fifth, and decisively for the project's priorities, the three 25 % domains account for three-quarters of the assessment weight, and the table shows the architecture serving them heavily: routing, segmentation and redundancy under Domain 3; directory, name resolution, file, storage, PKI, monitoring and automation services under Domain 4; and the deliberate fault injection, denied-flow capture, failover transitions and routing-loop exercise under Domain 6.
